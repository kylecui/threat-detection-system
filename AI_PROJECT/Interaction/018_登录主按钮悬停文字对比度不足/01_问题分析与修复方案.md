## 2. 问题描述、复现与证据

### 2.1 表现与预期

登录页主按钮正常显示时，背景为蓝青色、文字为白色；鼠标悬停后背景变亮，14px 白字对比度由约 4.64:1 降到约 3.65:1。

普通登录和首次管理员创建共用该主按钮主题，因此“登录”和“创建管理员并登录”两个状态均受影响。预期是在保留蓝青视觉方向的同时，各启用交互状态下的普通字号文字都达到至少 4.5:1。

### 2.2 复现步骤

1. 打开 `/login`，等待 bootstrap 状态检查完成。
2. 确认 `.tds-login__submit button[type="submit"]` 为启用状态，读取最终计算文字色、背景色、字号及字重。
3. 鼠标移入按钮，等待背景/文字色过渡完成，再读取计算样式。
4. 按 WCAG 相对亮度公式计算两种状态的文字对比度。

本次重查时，`Login/index.tsx`、`index.css`、`login.spec.ts` 的 SHA-256 仍与 017 交付及复查记录一致，既有浏览器证据适用于当前代码：

| 状态 | 最终背景 | 最终文字 | 字号/字重 | 对比度 |
| --- | --- | --- | --- | --- |
| 正常 | `#087f9c` | `#ffffff` | 14px / 600 | 4.6397:1 |
| 悬停 | `#2392a8` | `#ffffff` | 14px / 600 | **3.6532:1** |

14px/600 不属于可按大字号放宽阈值的文字。标准依据为 [W3C WCAG 2.2：Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)，其说明包括悬停及焦点状态的文字。

既有实测证据：[独立浏览器探测 JSON](../017_登录页与客户端双栏参考样式不一致/evidence/03-review/independent-browser-probe.json)，取 `desktop-zh` 的 `idle`、`hover` 数据。

## 3. 根本原因

### 3.1 正常主色不等于全部交互状态颜色

`frontend/src/pages/Login/index.tsx:33-60` 建立了 `inherit: false` 的局部浅色主题，但第 37 行仅设置：

```tsx
colorPrimary: "#087f9c",
```

没有显式设置 `colorPrimaryHover`。当前锁定的 Ant Design 为 **5.27.6**，其默认主题算法从正常主色推导出更亮的 `colorPrimaryHover=#2392a8`。按钮仍使用白字，导致 hover 状态不合格。

本阶段以当前本地依赖调用 `theme.getDesignToken` 重新核对，得到相同派生结果，与 017 的真实 Chromium 测量一致；这不是仅凭截图观感作出的判断。

### 3.2 当前状态样式还受到 CSS 优先级影响

`frontend/node_modules/antd/es/button/style/index.js:364-369` 的实心按钮状态规则直接使用 `colorPrimaryHover` 和 `colorPrimaryActive`。

项目 `frontend/src/index.css:1323-1359` 同时包含按钮颜色过渡、全局 active 背景及 focus-visible 轮廓。Ant Design 生成样式有自己的选择器权重，不能仅凭源码顺序认定哪个规则最后生效。因此下一阶段应读取真实 DOM 的最终计算颜色，而不是只看 Token 数值。

当前派生的 active Token 为 `#005a75`，对白字约 7.72:1，本身已合格；没有证据要求预先修改 active 色或全局规则。

### 3.3 原有回归未覆盖此状态

`frontend/e2e/login.spec.ts:288-301` 的主题检查只读取页面、表单栏和输入框背景是否为浅色，不采集主按钮文字/背景的组合，更不执行 hover 对比度检查。因此原有 25/25 通过与该缺陷可以同时存在。

## 5. 详细修复步骤

### 步骤 1：保留正常主色，显式定义局部 hover 色

建议在 `loginTheme.token` 中增加：

```tsx
// 下一阶段拟实施的局部配置示意，本阶段未写入源码。
colorPrimary: "#087f9c",
colorPrimaryHover: "#066b84",
```

候选颜色的计算结果：

| 候选背景 | 白字对比度 | 处理建议 |
| --- | --- | --- |
| 正常 `#087f9c` | 4.6397:1 | 保持现状 |
| hover `#066b84` | 6.0975:1 | 作为建议起点，实际 DOM 复验后采用 |
| 现有派生 active `#005a75` | 7.7225:1 | 暂不改；核对最终层叠结果 |

这保留了原蓝青色、白字和卡片设计，只让鼠标悬停反馈更深、更清晰。无需增加主题依赖、修改用户偏好、调整认证状态或添加全局 `!important`。

### 步骤 2：核对正常、hover、focus、active 的实际结果

1. 对真实提交按钮分别测量无悬停正常态、鼠标 hover、键盘 Tab focus-visible、保持鼠标按下的 active，以及 hover+active 组合。
2. 每次先让上一状态退出。例如测键盘焦点时，鼠标先移出按钮，避免把 hover 色误记为单独 focus 色。
3. 项目存在 160ms 颜色过渡。使用有界的过渡完成/颜色终值稳定等待；不要在状态切换瞬间采样，也不要等待包含无限旋转加载动画的所有全局动画结束。
4. 在鼠标仍按下时读取 active，再在 `finally` 中松开；若只在 mouseup 后采样，得到的不是 active。
5. 按实际 `color`、`backgroundColor` 计算，而非断言某个 CSS 字符串必须等于候选色。若遇透明颜色，先解析实际合成背景；无法解析应报错，不能返回一个假定合格值。
6. active/focus 最终结果合格即保留原实现；只有实测不合格时才补登录局部状态 Token，并记录原因。

### 步骤 3：增加防回归用例

- 在 `login.spec.ts` 增加独立状态对比场景，不替换已有浅色入口/主题保留用例。
- 普通登录与首次创建按钮均测试；至少覆盖中文和英文文字，以及保存 light/dark、系统深色三类入口的关键组合。
- 启用状态文字与背景至少为 4.5:1，不通过四舍五入把低于阈值的结果判为合格。
- disabled 状态有规范例外，单独检查可识别性和不可提交行为，不强行套用启用态的对比阈值，也不把启用按钮临时设为 disabled 来规避问题。
- 加载时保留原反馈、稳定可访问名称和禁止重复请求的行为；不能为了采样而向真实服务提交账号。

### 步骤 4：回归影响范围并更新结果

局部 `colorPrimaryHover` 可能同时影响同一 ConfigProvider 内输入框的 hover 边框等主色状态。检查用户名、密码输入框的 hover/focus，确认标签、错误提示、焦点环和密码显隐按钮仍清晰。

实施后在本目录生成 `02_修复结果.md`，记录采用的最终颜色、状态测量、实际命令及证据。不要覆盖 017 原始失败证据；两个问题都整改后，再关联回 017 进行整体复查。

## 6. 潜在影响与约束

- 只改 `loginTheme`，不要改全局 `createAppTheme` 或 `.ant-btn-primary`，避免波及工作台其他按钮。
- 正常主色、品牌图标、卡片宽高、53/47 比例及手机版式保持原方向。
- 不改变状态提示色、密码策略、API 路径、表单校验、首次创建及认证持久化。
- 不用提高字号或改字重规避阈值，因为这会改变已确认的表单比例。
- 新测试必须正确区分 normal/hover/focus/active，避免 CSS 过渡或残留鼠标状态造成误报。

## 8. 分析结论

根因是局部主题遗漏 hover 色配置，导致框架派生浅色背景与白字对比不足。建议先显式补一个足够深的登录局部 hover Token，再以实际浏览器状态验证，避免扩大修改范围。
