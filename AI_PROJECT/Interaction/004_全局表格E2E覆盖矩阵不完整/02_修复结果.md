## 2. 修复结果总结

1. **展示面清单 `TABLE_SURFACES`**（`e2e/helpers/tableSurfaces.ts`）：共 19 个展示面，覆盖全部 24 张表，每张表**恰好由一个展示面**负责。每个展示面声明以下内容：
   - 路由（或测试专用页面）、角色；
   - 作用域：主内容 / Modal / Drawer；
   - 进入步骤：切换视图、展开行、切换 Tab、打开抽屉或弹窗、加载锁定数据；
   - **精确的预期表格数**；
   - 各视口的模式：表格或卡片，以及卡片的选择器；
   - 对应的源码实例（文件 + 序号）。

   静态契约 `test_table_surfaces_cover_all_24_instances_once` 用源码扫描结果核对这份清单：新增或删除表格而未更新清单时会失败。
2. **交互场景全部固化**：

   | 展示面 | 进入方式 | 覆盖的表 |
   | --- | --- | --- |
   | `overview` | `/overview` | 最新威胁、Top 攻击者（768/390 断言移动卡片） |
   | `alerts-grouped-expanded` / `alerts-detail` | 分组视图并展开首行 / 详情视图 | 告警 3 张 |
   | `threats-grouped-expanded` / `threats-detail` | 同上 | 威胁 3 张 |
   | `intel-indicators` / `intel-feeds` | 两个 Tab | 情报 2 张 |
   | `pipeline` / `ml` | 路由（390 断言移动卡片） | 各 1 张 |
   | `customers` / `customers-device-list` | 客户 Tab / 设备管理 Tab | 客户、设备列表 |
   | `customers-device-drawer` | 点击“设备”打开**抽屉** | 设备抽屉表 |
   | `customers-device-events-modal` | 抽屉内点击“数据流”打开**弹窗** | 攻击事件表 |
   | `users` / `tenants` / `ai-config` / `plugins` | 路由 | 4 页 5 张 |
   | `config-cascading` / `config-cascading-members-modal` | 测试专用页面：加载锁定数据 / 打开成员**弹窗** | 配置级联 3 张 |

3. **作用域与生产 CSS 一致**：主内容用 `.tds-content`，弹窗用 `.ant-modal-root .ant-modal`，抽屉用 `.ant-drawer-open .ant-drawer-content`，并只检查可见元素。
4. **显式响应式矩阵，无通用跳过**：
   - 快速档（默认，适合提交前）：19 个展示面 × {1440 英文浅色、390 英文浅色、1440 中文浅色、1440 英文深色}，共 **76** 个用例。
   - 完整档（`TABLE_MATRIX=full`）：19 个展示面 × 6 个视口（1920×1080、1440×900、1280×800、1024×768、768×1024、390×844）× 中/英 × 浅/深，共 **456** 个用例。
   - 两档共用同一份清单。移动卡片断言计为“通过”。缺表时等待 30 秒后失败，不再跳过。
5. **语言与主题**：
   - 语言通过 `setAuthState(..., language)` 写入 `tds-lang`。
   - 主题通过新增的 `setTheme()` 在页面脚本执行前写入 `tds-theme`，并断言 `html[data-theme]` 确实切换。
   - 定位器使用生产翻译文件中的文案（`helpers/locale.ts` 的 `tr()`），所以中英文都用真实文字定位。
6. **几何与可用性断言**（`helpers/tableAssertions.ts`，在页面内执行，对每张可见表）：
   1. 表头和数据单元格的 `text-align: center`、`vertical-align: middle`、`white-space: nowrap`；
   2. 复合内容的几何中心偏差 ≤3px（检查对象：操作组、多标签、状态标签、开关、IP/MAC 标识、复选框、排序与筛选的“标题 + 图标”整体，不是整个 flex 容器）；
   3. 操作组中的按钮在同一行，且不越出单元格；
   4. 表格中每个按钮都有可访问名称；
   5. 表头与首行各列左右边界对齐，偏差 ≤1px，滚动前后都检查；
   6. 表格内容溢出时，真实设置 `scrollLeft`，确认确实发生滚动、`overscroll-behavior-x: contain` 生效，固定在右侧的列仍在可视区内，并用 `elementFromPoint` 确认其中按钮没有被遮挡、可以点击；
   7. 作用域本身（以及 `.tds-content__inner`、弹窗正文、抽屉正文）不得比其可视宽度更宽，用来拦截被 `overflow: hidden` 静默裁掉的内容；
   8. 深色/浅色主题下普通文本单元格的对比度 ≥4.5；
   9. 页面根节点无横向溢出；
   10. 长文本：确有溢出的 `TableCellText` 悬停后显示完整值，未溢出的悬停后不出提示。

   就绪判定为“预期表格齐全、有数据、无加载转圈、弹窗/抽屉动画结束，并持续 1 秒”。只有就绪判定会轮询，布局断言只执行一次、不重试。
7. **错误监控**：每个用例都检查 `pageerror`、未登记的 `console.error`（白名单只有 antd 开发版废弃提示）、未知 API 请求（003）。
8. **功能回归**（`e2e/table-interactions.spec.ts`，6 个用例）：
   - 排序（概览 Top 攻击者点击表头后顺序改变）；
   - 行选择（威胁明细勾选后行进入选中态）；
   - 展开行（告警分组）；
   - 配置级联图标操作：编辑/批量分配打开弹窗，删除/移除弹出确认；
   - 键盘 Tab 可达且出现 `:focus-visible`；
   - 设备抽屉操作：分组语义、解绑确认、编辑弹窗。
9. **ConfigCascading 的测试入口**：新增测试专用页面 `e2e/harness/config-cascading.html` + `.tsx`，使用生产的 Provider、全局样式、i18n 和主题 Token，外壳与路由一致（`.tds-content > .tds-content__inner > .tds-route-stage`）。
   - **没有新增生产路由**。该页面只由 Vite 开发服务器提供；生产构建入口只有 `index.html`，镜像只拷贝 `dist/`。
   - 为了让测试页使用与生产完全相同的 Token，把 `App.tsx` 中内联的 antd 主题对象原样抽成 `src/theme/appTheme.ts` 的 `createAppTheme()`，`App.tsx` 改为调用它（值与结构未改）。
10. **本矩阵发现并修复的真实缺陷**：带 `responsive` 隐藏列的表格，在窄屏仍使用“全量列宽和”作为 `scroll.x`。剩余列会被拉伸到该宽度，固定在右侧的操作列甚至比可视区还宽：
    - 390px 下情报订阅源的操作列 337px，可视区只有 311px；
    - 告警明细的操作列 348px，可视区 315px；
    - 设备抽屉同样受影响。

    这是 `INTERACTION-001` 设定 `scroll.x` 时遗漏的情形。修复方式：新增 `useResponsiveScrollX(columns)`，按当前断点下实际渲染的列计算 `scroll.x`，判定规则与 antd 隐藏列的规则一致。告警明细、威胁明细与分组展开的嵌套表（两者共用一个预算）、情报订阅源、设备抽屉、设备攻击事件，共 6 个表格实例已改用它。静态契约随之新增“含 `responsive` 列的表必须使用该钩子，且必须基于自己的列”。

### 4.1 完整矩阵结果

| 轮次 | 结果 | 处理 |
| --- | --- | --- |
| 第 1 次完整运行（6 个 worker） | 451 通过、5 失败 | 失败全部是时序问题：客户 ProTable 在作用域确定后会再请求一次，最终检查恰好遇到二次加载的转圈；2 核机器上告警明细加载超过 15 秒。改为“就绪状态需持续 1 秒、上限 30 秒”，只轮询就绪判定，布局断言不重试 |
| 新增“内容裁切”检查后的快速档 | 发现 2 个真实问题 | 根因不在表格（见 4.2），做精确登记 |
| 第 2 次完整运行（3 个 worker） | **452 通过**、4 失败 | 4 个失败都是已知问题的适用范围需细化：NEW-A 在 768 也出现但只在英文，NEW-B 只在英文出现（中文按钮较短，“问题已不再出现”的保护机制正确触发）。登记改为按“视口 + 语言”精确匹配 |
| 对受影响的 2 个展示面重跑完整矩阵 | **48/48 通过** | — |
| **最终代码一次性完整运行**（3 个 worker，13.8 分钟） | **456/456 通过，0 跳过** | 报告注释：`known-issue` 8 条（仅限登记的“展示面 + 视口 + 语言”组合）；`local-umd-build` 96 条（4 张 ProTable × 24 个组合，仅表示本地未检查其深色对比度） |

### 4.2 已登记的已知问题（非表格缺陷，建议另立编号）

完整矩阵的“内容裁切”检查发现了 2 个**不属于表格本身**的窄屏问题。按方案 §6，没有放宽检查，而是在 `KNOWN_ISSUES` 中做了精确登记：只放行指定展示面、指定视口上的那一条问题文本；测试报告中带 `known-issue` 注释；问题一旦不再出现，用例会失败，提醒删除登记。

| 登记编号 | 展示面 / 视口 | 现象 | 根因定位 |
| --- | --- | --- | --- |
| NEW-A（建议 `INTERACTION-006`） | 设备“数据流”弹窗 / 390 | 弹窗正文内容 877px，正文可视宽 332px | 表格上方的设备概要 `Descriptions` 为多列布局，手机上未收成单列；表格本身已在内部横向滚动 |
| NEW-B（建议 `INTERACTION-007`） | 配置级联 / 390 | 内容 425px，容器 375px，被 `.tds-content` 的 `overflow-x: hidden` 裁掉 | 锁定查询表单中的 3 个文字按钮（`<Space>` 未开启换行）总宽 395px |

> **后续更新（2026-10-28）**：NEW-A、NEW-B 已分别由 `INTERACTION-006`、`INTERACTION-007` 修复。两条登记已从 `KNOWN_ISSUES` 删除（现为空列表），完整矩阵在无任何豁免的情况下 456/456 通过。详见两个问题文件夹中的 `02_修复结果.md`。

## 5. 与方案的差异与限制

| 方案 | 实际 | 原因 |
| --- | --- | --- |
| 浏览器缩放 80/100/125/150/200% 的真实缩放验收 | **未自动化**，也未在本轮执行 | 无头 Chromium 无法真实控制浏览器缩放；方案明确不得用 CSS `zoom` 或 `deviceScaleFactor` 冒充。需在真实 Chrome 中人工执行（步骤见第 6 节），不能写成“已自动化通过” |
| 快速档“高风险展示面 + 1440/390 + 中英关键组合” | 快速档覆盖**全部** 19 个展示面 | 单次只需约 2 分钟，没有必要只抽高风险面 |
| “每类交互至少一次真实操作”中的筛选、搜索、分页 | 已覆盖排序、选择、展开、Tab、抽屉、弹窗、操作按钮、确认框；**筛选/搜索/分页未单独新增用例** | 原有 `audit-regression`、`threat-list`、`threat-intel` 等用例已覆盖筛选、搜索和导出，且回归结果不变；分页受夹具数据量限制（每表 1–3 条） |
| ConfigCascading 测试入口 | 测试专用页面（不进入生产包） | 组件仍未挂载生产路由，按方案不擅自暴露路由；去留仍待产品决策 |

## 6. 未解决问题与注意事项

1. **真实浏览器缩放验收（人工）**：在真实 Chrome 中打开 1440×900 窗口，用 `Ctrl+-`/`Ctrl+=` 依次切到 80%、100%、125%、150%、200%。每档逐个打开第 2 节的 19 个展示面，记录 `window.devicePixelRatio` 和截图，确认单行、居中、表格内部可横向滚动、页面无横向滚动条。
2. 第 4.2 节两个新问题需另立编号处理。
3. 第一次在本机运行完整档前，请先执行 `npx playwright install chromium`，或像复查报告那样设置 `PLAYWRIGHT_EXECUTABLE_PATH` 指向系统 Chrome。
4. 若本机开发模式下出现新的已知无害控制台错误，应逐条加入 `CONSOLE_ALLOWLIST` 并写明理由，不能关闭检查。
5. `E2E_LOCAL_UMD_BUILD=1` 只在本次无依赖环境使用；**在本机 `npm run dev` 下不要设置**，以保证 ProTable 也执行对比度检查。
