# 004 全局表格 E2E 覆盖矩阵不完整——问题分析与修复方案

## 1. 文档信息

- 问题编号：`INTERACTION-004`
- 来源：`001_全局表格对齐与单行显示规范/03_复查验收报告.md` 的第三个遗留问题
- 优先级：P2
- 当前阶段：仅分析与制定方案，未修改源码
- 前置依赖：先完成 `INTERACTION-003`，确保 Mock 和失败判定可信
- 问题类型：全量回归覆盖、响应式、主题与国际化、Portal 表格、可访问性

## 2. 问题描述

现有静态契约盘点到 24 张 `Table/ProTable`，但浏览器 E2E 只是对 11 个路由、3 个视口下“当前可见的主内容表格”做通用检查。它没有证明 24 张表的每一个实际展示状态都被打开和验证，也没有覆盖原始要求中的完整分辨率、缩放、语言、主题、弹窗和抽屉场景。

因此当前结论只能说明“已抽查的可见表格符合规则”，不能证明“整个项目所有表格在各场景下都符合规则”。

## 3. 代码排查结果

### 3.1 当前 E2E 的覆盖边界

| 文件与位置 | 当前行为 | 缺口 |
| --- | --- | --- |
| `frontend/e2e/table-layout.spec.ts:11-23` | 11 个路由 | 路由不等于表格实例；Tab、展开行、弹窗、抽屉中的表未必出现 |
| `frontend/e2e/table-layout.spec.ts:25-29` | 1440、1024、390 三档 | 缺少 1920、1280、768；没有浏览器缩放矩阵 |
| `frontend/e2e/table-layout.spec.ts:36-44` | 页面进入后找第一张可见表；没有则跳过 | 无法确认预期表格数量，也会掩盖加载失败 |
| `frontend/e2e/table-layout.spec.ts:48-50` | 只选择 `.tds-content .ant-table` | Portal 到 `body` 下的 `.ant-modal`、`.ant-drawer` 不在范围内 |
| `frontend/e2e/table-layout.spec.ts:53-60` | 检查 `text-align`、`vertical-align`、`white-space` | 未检查文本遮挡、重要信息裁切后的 Tooltip、表头/数据实际几何中心 |
| `frontend/e2e/table-layout.spec.ts:62-67` | 只比较按钮 `top` 是否一致 | 只能发现换行，不能发现按钮组整体偏左/偏右 |
| `frontend/e2e/table-layout.spec.ts:68-77` | 检查页面根节点无横向溢出 | 没有实际滚动表格容器，也没有验证固定操作列滚动后仍可用 |

合计 24 张。现有路由循环无法自动切换所有 Tab、模式、展开行，也不会点击按钮打开抽屉/弹窗，因此“路由已覆盖”不能等同于“表格已覆盖”。

### 3.3 ConfigCascading 的特殊问题

- `frontend/src/pages/Configuration/index.tsx:62-74` 会在管理员 Tab 中渲染 `ConfigCascading`。
- `frontend/src/App.tsx:1189-1225` 采用拆分后的配置路由，没有挂载 `Configuration` 聚合组件。
- `/configuration` 在 `App.tsx:1260-1262` 只重定向到 `/config/general`。

因此 ConfigCascading 的三张表不能通过现有生产路由进入。测试方案必须先决定组件保留/恢复/退役，不能为了凑覆盖率擅自暴露生产路由。

### 3.4 主题与语言入口

- 主题持久化键：`frontend/src/contexts/ThemeContext.tsx:10-38` 的 `tds-theme`，值为 `light`/`dark`，并写入 `html[data-theme]`。
- 语言持久化键：`frontend/src/i18n/index.ts:16-20` 的 `tds-lang`，值为 `zh-CN`/`en-US`。
- `frontend/e2e/helpers/auth.ts:205-240` 已支持传入语言，但当前表格 E2E 固定使用默认英文，且没有设置主题矩阵。

## 4. 根本原因

### 4.1 测试模型以“路由”为中心，而不是以“表格展示面”为中心

一个路由可以包含多个 Tab、模式、展开行、抽屉和弹窗。简单遍历 URL 无法到达这些状态。

### 4.2 选择器作用域与生产 CSS 作用域不一致

生产规则已经覆盖 `:is(.tds-content, .ant-modal, .ant-drawer)`，E2E 却只检查 `.tds-content`，导致最需要验证的 Portal 场景缺席。

### 4.3 没有声明每个视口应出现表格还是替代卡片

响应式切换是业务设计的一部分。当前动态 skip 既没有验证表格，也没有验证替代视图。

### 4.4 完整矩阵没有分层执行策略

24 张表 × 6 视口 × 2 语言 × 2 主题，再叠加缩放会产生较大执行量。没有“提交级快速回归”和“完整验收矩阵”的分层，最终只保留了小规模抽查。

### 4.5 自动化断言只检查计算样式，没有检查真实空间关系

文本 `text-align: center` 不代表复合组件在视觉上真正居中；同样，存在滚动宽度也不代表用户可以滚动并操作固定列。

## 5. 建议修复方案

### 5.1 建立表格展示面清单 `TABLE_SURFACES`

每个展示面至少声明：

- 唯一 ID。
- 路由或组件测试入口。
- 所需角色。
- 进入后的操作步骤：切换 Tab、切换详情/分组、展开行、打开抽屉/弹窗。
- 作用域：主内容、Modal 或 Drawer。
- 各视口下的预期模式：`table`、`cards` 或明确空态。
- 预期可见表格数量或稳定的表格标识。
- 对应 Mock fixture。

不能再以“找到任意一张表”作为整页通过条件。

### 5.2 逐类固化交互场景

1. 告警中心：分别进入详情视图、分组视图，并展开一行检查嵌套表。
2. 威胁列表：分别验证详情、分组和分组展开表。
3. 威胁情报：切换“威胁指标/订阅源管理”两个 Tab。
4. 客户与设备：切换设备管理，打开设备抽屉，再打开攻击事件/数据状态相关视图；把此前手工验证固化为自动化。
5. AI 配置：确保供应商表和配置分配表都可见并分别断言。
6. ConfigCascading：
   - 若确认恢复产品入口，按真实入口测试；
   - 若仅保留组件，使用不进入生产包的测试专用浏览器 Harness 或组件浏览器测试；
   - 若确认退役，另行删除后更新 24 张表清单。
7. Modal/Drawer 选择器改为与生产 CSS 一致的 `:is(.tds-content, .ant-modal, .ant-drawer)`，并限定到当前打开的 Portal，避免读到隐藏 DOM。

### 5.3 显式响应式矩阵

完整验收至少包含：

- 1920×1080
- 1440×900
- 1280×800
- 1024×768
- 768×1024
- 390×844

对移动端采用卡片的页面，不跳过测试，而是断言替代卡片可见、数据完整、无横向页面溢出。对仍使用表格的窄屏页面，断言内部滚动和固定操作列。

### 5.4 语言与主题矩阵

1. 通过 `setAuthState(..., 'zh-CN'/'en-US')` 分别执行中英文。
2. 在页面脚本执行前写入 `localStorage['tds-theme'] = 'light'/'dark'`。
3. 断言 `html[data-theme]` 与预期一致，避免只写存储值但页面未切换。
4. 长英文表头、按钮提示、状态标签和时间字段必须保持单行；深色主题下文字、标签和固定列阴影不能丢失对比度。

### 5.5 浏览器缩放验证

原始验收要求包含 80%、100%、125%、150%、200%。浏览器缩放不能用 CSS `zoom`、`deviceScaleFactor` 或单纯改变 viewport 冒充。

建议建立独立的真实 Chrome 验收任务：

1. 使用 headed Chrome 的浏览器快捷键或受控浏览器能力调整真实页面缩放。
2. 每次缩放后验证 `devicePixelRatio`/可视区域指标确实变化，并记录截图和测量结果。
3. 若 CI 环境无法可靠控制浏览器缩放，应明确保留为人工/专用浏览器验收矩阵，保存证据；不能在报告中写成“已自动化通过”。
4. CSS `zoom` 只能作为补充压力测试，不得替代真实浏览器缩放验收。

### 5.6 扩充几何与可用性断言

对每个可见表格检查：

1. 表头和数据单元格 `text-align: center`、`vertical-align: middle`、`white-space: nowrap`。
2. 单元格内容包围盒中心与单元格中心偏差在 2–3px 容差内，重点检查操作按钮组、Tag、Switch、Checkbox、IP/MAC 和时间。
3. `.tds-table-actions` 中按钮同一行，组中心与单元格中心一致。
4. 根节点 `scrollWidth <= clientWidth`。
5. 表格内容区有溢出时，设置 `scrollLeft` 后数值确实变化；固定右侧操作列仍可见、可点击。
6. 长文本只有实际溢出时显示 Tooltip；Hover 后 Tooltip 能读到完整值。
7. 表头与数据列边界对齐，固定列滚动前后无错位。
8. 捕获 `pageerror`、非预期 `console.error` 和未知 API 请求。

### 5.7 分层执行，控制测试成本

- 提交级快速矩阵：高风险展示面 + 1440/390 + 中英文关键组合，必须无静默 skip。
- 夜间/发布前完整矩阵：24 张表全部展示面、6 视口、2 语言、2 主题。
- 缩放矩阵：独立 Chrome 验收任务，可与完整矩阵并行，但必须有真实证据。
- 所有层级共用同一个 `TABLE_SURFACES` 清单，避免快速测试和完整测试维护两套事实来源。

## 6. 潜在影响

- 完整矩阵会增加运行时间，需要拆分项目或并行执行，不能因此减少验收项。
- 打开抽屉、弹窗、展开行需要稳定的语义定位器；优先使用角色和可见名称，确有必要时再增加稳定 `data-testid`。
- 中英文文案变化可能使基于完整文本的定位器变脆，应使用角色 + 稳定业务语义，而不是 DOM 层级。
- ConfigCascading 的可达性是产品决策，不应由测试代码擅自改变。
- 真实浏览器缩放在无头环境中不稳定，必须如实区分“自动化”“专用浏览器”“人工证据”。
- 严格检查可能发现现存问题；发现后应新增独立问题，不得通过放宽容差或增加 skip 隐藏。

## 7. 验证方法与验收标准

### 7.1 清单完整性

- 静态扫描仍为 24 张表时，`TABLE_SURFACES` 能关联到全部 24 张。
- 新增或删除表格会使清单契约失败并提示更新。
- 每个 Portal/Tab/展开表都有明确进入步骤和预期数量。

### 7.2 自动化结果

- 6 个视口、中英文、浅色/深色均有可重复执行结果。
- 不存在“因为没找到表格而跳过”的通用逻辑。
- 移动卡片通过卡片断言计入通过，不计入跳过。
- 主内容、Modal、Drawer、嵌套表都执行同一套对齐与单行检查。
- 页面根节点横向溢出为 0；需要滚动的表格可以实际滚动。
- 操作组、状态标签、IP/MAC、时间的几何中心满足容差。
- `pageerror`、未知 API、非预期控制台错误为 0。

### 7.3 功能回归

验证过程中不得破坏排序、筛选、搜索、分页、行选择、Tab、展开行、固定列和操作按钮。至少对每类交互执行一次真实操作，而不是只检查静态 DOM。

### 7.4 通过标准

只有在 24 张表均能关联到可重复验证证据、完整矩阵无遗漏、预期替代视图有正常断言、没有静默跳过时，才可把 `INTERACTION-001` 的“全局覆盖”结论升级为通过。

## 8. 本阶段结论

当前缺口的根因是测试以 URL 和“任意可见表格”为粒度，未建模真实的表格展示面。建议先修复 `INTERACTION-003` 的数据契约，再建立清单驱动、Portal 感知、响应式显式声明的完整矩阵。本阶段未修改测试或生产代码。
