## 2. 问题描述、复现与证据

### 2.1 现象与期望

当前密码显隐按钮支持 Tab 聚焦、空格和 Enter，正常单击及两次独立按键工作正常。但持续按住空格时，操作系统会发出自动重复的 keydown，每个重复事件都再次切换显隐；松开后的状态取决于重复次数，反馈不稳定。

期望对一次持续按住的动作只切换一次；松开后重新按键才再次切换。焦点应留在对应显隐按钮，密码内容不变，`aria-pressed` 与“显示/隐藏密码”名称始终同步，不触发登录或首次创建请求。

### 2.2 复现步骤

1. 打开普通登录页，在密码框输入测试文本，用 Tab 聚焦显隐按钮。
2. 按下并保持空格，产生至少一次系统重复 keydown，再松开。
3. 观察密码是否在显示/隐藏之间多次切换。
4. 在首次管理员创建模式下，对密码和确认密码分别重复上述操作。

017 已保存真实 Chromium 事件和状态序列；本次核对相关文件哈希仍一致。

证据：[space-repeat.json](../017_登录页与客户端双栏参考样式不一致/evidence/03-review/space-repeat.json)。两个输入框都记录为：

```text
键盘事件：keydown repeat=false → keydown repeat=true → keyup repeat=false
输入类型：password → text → password → password
```

焦点保持在按钮、输入值长度未变，说明不是“空格输入到了密码中”，而是重复事件实际多次触发了切换。增加重复次数还会继续翻转。

## 3. 根本原因

### 3.1 自定义 keydown 将自动重复当成新操作

`frontend/src/pages/Login/index.tsx:133-140` 的当前逻辑为：

```tsx
if (event.key === " " || event.key === "Enter") {
  event.preventDefault();
  event.stopPropagation();
  const button = event.currentTarget;
  button.click();
  button.focus({ preventScroll: true });
}
```

处理没有判断 `event.repeat`。因此首次按下与保持按住所产生的重复事件都会进入 `button.click()`。同一分支也处理 Enter，下一阶段应一并覆盖 Enter 的重复键事件，避免同类缺口。

### 3.2 Ant Design 已负责真正的显隐切换

当前锁定 Ant Design 5.27.6 的 `antd/es/input/Password.js`：

- 第 23-25、30 行：默认通过 click 触发。
- 第 48-60 行：内部维护 visible 并执行实际翻转。
- 第 65-80 行：克隆 `iconRender` 元素，注入 `onClick`、样式类和鼠标事件；自定义 `onKeyDown` 继续存在。

所以应用中的 `button.click()` 已会进入框架的真实切换链路，不需要再新增 visible 状态或第二套切换事件。

### 3.3 焦点恢复有实际依赖，不能随手删除

`rc-input/es/BaseInput.js:39-43` 的后缀 click 冒泡处理会把焦点放回输入框。因此当前第 140 行恢复按钮焦点，是为了解决此前“第二次空格进入密码框”的问题；它应与本次重复事件修复同时保留。

### 3.4 现有测试只验证独立按键

`frontend/e2e/login.spec.ts:557-566` 执行两次 `keyboard.press("Space")`，每次都是独立的按下/松开，不会构造按住时的 `repeat=true`。该用例可以通过，但不能证明长按安全。

## 5. 详细修复步骤

### 步骤 1：在正确的位置屏蔽重复事件

建议保留现有处理方式，仅在每次取消默认行为和冒泡后加入重复判断：

```tsx
// 下一阶段拟实施的逻辑示意，本阶段未写入源码。
if (event.key === " " || event.key === "Enter") {
  event.preventDefault();
  event.stopPropagation();
  if (event.repeat) return;

  const button = event.currentTarget;
  button.click();
  button.focus({ preventScroll: true });
}
```

**顺序不能颠倒**：若先 `if (event.repeat) return`，只是略过手工 click，当前重复事件的原生默认行为却没有取消，尤其 Enter 仍可能触发原生按钮激活，绕过防护。每一个被识别的 Space/Enter 事件都应先取消默认行为及冒泡。

该方案无需新增 ref、计时器、节流间隔、可见状态或全局键盘监听；两次独立按键各自 `repeat=false`，因此仍能分别切换。

### 步骤 2：保留原有框架事件和可访问性

- `type="button"` 保持不变，不能变为 submit。
- 继续由 Ant Design 注入的 click 管理 visible，不另加应用层翻转、不补一个再次切换的 keyup handler。
- 保留 `button.focus({ preventScroll: true })`，防止后缀冒泡再次把焦点留在输入框。
- 保留动态 `aria-label`、`aria-pressed`、装饰图标隐藏、Tab 顺序、44px 热区和可见焦点。
- 不添加字符串过滤来“删除多余空格”，不修改密码值、输入位置、自动补全或确认密码校验。

### 步骤 3：为长按添加真实事件回归

用 Playwright 在真实浏览器构造长按周期：

```text
keyboard.down('Space')   // 第一次，repeat=false
keyboard.down('Space')   // 重复，repeat=true
keyboard.down('Space')   // 再重复，repeat=true
keyboard.up('Space')     // 松开
```

Enter 使用同样的周期单独验证。建议在页面临时记录键事件的 repeat 标记作为测试证据，防止误把多次完整 `press()` 当作长按。

每一组在 `finally` 中释放按键，避免某个断言失败后键盘仍处于按下状态，影响后续用例。不要依赖等待操作系统自动重复的长时间 sleep，也不要通过降低断言强度或增加 retry 获得通过。

### 步骤 4：在有效表单中验证“没有误提交”

显隐操作时应填写确实能通过本地校验的用户名、密码及必要的确认字段，并隔离拦截 `/api/v1/auth/bootstrap`、`/api/v1/auth/login` POST。

整个显隐操作周期中，两类 POST 次数均应为 **0**；初始化状态 GET 不计入。若使用空表单，原有校验会挡住误提交，容易得到“没有请求”的假通过结果。

## 8. 分析结论

根因是公共显隐按钮对每次 Space/Enter keydown 都执行 click，没有区分初次按下与系统自动重复。建议在现有默认行为取消逻辑后补 `event.repeat` 防护，保留框架切换及焦点恢复，以最小变更关闭该边界问题。
