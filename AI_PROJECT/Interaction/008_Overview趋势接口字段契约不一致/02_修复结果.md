## 2. 修复结果总结

1. **新增 API 传输类型 `ThreatTrendPoint`**（`types/index.ts`）。
   - 字段与后端 `TrendDataPoint` 一一对应：`timestamp`（ISO 字符串）、`count`、`averageScore`、`maxScore`、`criticalCount`、`highCount`、`mediumCount`。
   - 后端对空时间桶也会把所有字段补 0，所以全部声明为必填，没有做成可选或字段并集。
   - `ChartDataPoint` 保留 `time/value/category`，注释改为“前端展示模型，不是 API 响应”。
2. **统一 3 个趋势入口的类型**：
   - `OverviewSnapshot.trend` 改为 `ThreatTrendPoint[]`；
   - `threatService.getThreatTrend`、`getTenantTrend` 的请求泛型和返回类型改为 `ThreatTrendPoint[]`；
   - 服务层不再引用 `ChartDataPoint`。
   - 全局搜索确认：这两个服务方法目前没有调用方；`ChartDataPoint` 只剩 Overview 的图表状态和新的映射函数在使用。
3. **单一、强类型的映射边界**：新增 `pages/Overview/trend.ts` 的纯函数 `toTrendChartData(points, hours, category)`。
   - 时间只读 `timestamp`：超过 48 小时按“月/日”，否则按“时:分”，规则与原来相同。
   - 数值只读 `count`。
   - `category` 仍是前端本地化文案。
   - Overview 删除了 `(item: any)` 和 `item.count ?? item.value ?? 0`，改为一行 `toTrendChartData(trend, hours, t('overview.threatCount'))`；并移除了不再使用的两个日期格式化导入。
4. **夹具只含真实字段**：
   - 删除临时类型 `OverviewTrendPoint = ChartDataPoint & { timestamp }`；
   - 新增 `THREAT_TREND`：2 个点，其中第 2 个是全 0 的空时间桶，模拟后端补零；
   - `OVERVIEW_SNAPSHOT` 直接 `satisfies OverviewSnapshot`；
   - 客户趋势、租户趋势两条 Mock 路由改为返回同一个 `THREAT_TREND`。
5. **防止回退**：
   - 类型层面：夹具再加 `time`/`value` 会触发 TS2353；页面或映射函数再读 `.value` 会触发 TS2339。
   - 测试层面：`api-mocks.spec.ts` 新增断言，3 个趋势来源的每个点都必须**恰好**是 DTO 的 7 个字段。

## 5. 与方案的差异

| 方案 | 实际 | 原因 |
| --- | --- | --- |
| 5.1.1 命名“`ThreatTrendPoint` 或 `ThreatTrendDataPoint`” | `ThreatTrendPoint` | 更短，且与后端 `TrendDataPoint` 区分开 |
| 5.3.6 “如需兼容旧部署，在服务层做版本化适配” | 未做兼容适配 | 后端 DTO 已明确且稳定（方案 3.5），方案要求页面不得接收联合形状。若确有旧部署返回 `time/value`，现在会显示为空值而不是静默兜底，需另行评估 |
| 7.2 契约验证“直接请求三个线上接口” | 未执行 | 工作区无法访问后端服务。另外，`TrendDataPoint.java` 等后端文件在项目里嵌套 9 层目录，超过本环境可读取的 7 层上限，未能直接读取。DTO 字段以方案 3.5 引用的 `TrendDataPoint.java:19-55` 为准，**请第三阶段对照后端源码或真实响应确认**，见第 6 节 |

## 6. 未解决问题与注意事项

1. **需在真实环境确认契约**：请直接请求以下 3 个接口，核对响应字段与 `ThreatTrendPoint` 的 7 个字段一一对应，且 `timestamp` 为可解析的 ISO 字符串、空时间桶为 `count: 0`：
   - `/api/v1/assessment/overview-snapshot`
   - `/api/v1/assessment/trend?customer_id=…&hours=24`
   - `/api/v1/assessment/trend/tenant?customer_ids=…&hours=24`

   如果后端 `timestamp` 实际序列化为数组或毫秒数（取决于 Jackson 配置），需同步调整类型说明；当前页面行为与修复前相同，因为原代码同样直接读取 `timestamp`。
2. **行为差异（有意为之）**：原代码在 `count` 缺失时回退到 `value`，再回退到 0。现在严格读取 `count`。后端补零逻辑正常时没有区别；如果后端返回了缺少 `count` 的异常数据，图表会出现空值而不是 0。按方案 6.4，这属于后端数据完整性问题，不在前端掩盖。
3. `getThreatTrend`、`getTenantTrend` 目前没有调用方。将来使用时，必须在展示边界调用 `toTrendChartData`（或另写同样强类型的映射），不能把结果直接交给图表。
