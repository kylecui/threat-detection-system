# 008 Overview 趋势接口字段契约不一致——问题分析与修复方案

## 1. 文档信息

- 问题编号：`INTERACTION-008`
- 优先级：P2
- 来源：全局表格与 E2E 覆盖复查时发现的前后端类型契约问题
- 当前阶段：仅分析与制定修复方案，未修改前端、后端、Mock 或测试
- 影响范围：威胁总览快照、客户趋势接口、租户趋势接口、Overview 趋势图及其 E2E Fixture

## 2. 问题描述

后端趋势接口实际返回字段为 `timestamp`、`count` 以及多个统计值；前端却把这些响应声明为用于图表渲染的 `ChartDataPoint`，该类型只有 `time`、`value`、`category`。Overview 页面为了兼容这两个互不一致的结构，使用 `any` 和 `item.count ?? item.value` 回退读取；E2E Fixture 又同时伪造 `time`、`timestamp`、`value` 字段以同时满足错误类型和当前运行代码。

当前页面之所以通常还能显示，是因为运行时返回的对象确实具有 `timestamp/count`，而 `any` 绕过了 TypeScript 检查。这不是契约正确，而是类型系统和测试都在掩盖真实接口形状。一旦接口调用被复用、重构掉回退逻辑，或 Fixture 与线上响应进一步分离，就可能出现时间格式化错误、趋势值变成 0、图表空白或测试假通过。

预期结果：前端存在与后端 DTO 一致的“接口传输类型”，Overview 在明确的映射边界把它转换为 `ChartDataPoint`；服务、快照、Mock 和测试全部使用同一真实字段名，不再依赖 `any` 或双形态 Fixture。

## 3. 根本原因

### 3.1 接口 DTO 与图表展示模型被混为同一类型

`frontend/src/types/index.ts:632-637` 的 `ChartDataPoint` 是纯展示模型：

```ts
interface ChartDataPoint {
  time: string;
  value: number;
  category?: string;
}
```

但 `frontend/src/types/index.ts:327-335` 把 `OverviewSnapshot.trend` 声明为 `ChartDataPoint[]`。这是概念层级错误：API 返回值尚未转换成图表模型。

### 3.2 两个趋势服务方法沿用了错误返回类型

- `frontend/src/services/threat.ts:108-119`：客户趋势接口声明返回 `ChartDataPoint[]`；
- `frontend/src/services/threat.ts:174-180`：租户趋势接口声明返回 `ChartDataPoint[]`。

对应后端控制器实际返回 `List<TrendDataPoint>`，不是 `ChartDataPoint`。

### 3.3 页面用 `any` 和兜底字段隐藏不一致

`frontend/src/pages/Overview/index.tsx:111-118` 中：

- 参数显式写成 `item: any`，阻止编译器发现字段不存在；
- 时间只读取 `item.timestamp`；
- 数值读取 `item.count ?? item.value ?? 0`。

同一段代码同时假定两种结构，无法保证哪一种才是正式契约。

### 3.4 E2E Fixture 为错误类型添加“双字段”补丁

`frontend/e2e/helpers/apiFixtures.ts:142-156` 明确记录了不一致，并定义：

```ts
type OverviewTrendPoint = ChartDataPoint & { timestamp: string };
trend: [{ time: T0, timestamp: T0, value: 3 }]
```

该 Fixture 并不等同于后端真实响应：真实响应使用 `count`，Fixture 使用 `value`，只是依赖页面回退逻辑通过测试。这会让测试无法发现生产契约回归。

### 3.5 后端契约本身已经明确且稳定

`services/threat-assessment/src/main/java/com/threatdetection/assessment/dto/TrendDataPoint.java:19-55` 定义：

- `timestamp`
- `count`
- `averageScore`
- `maxScore`
- `criticalCount`
- `highCount`
- `mediumCount`

`OverviewSnapshotResponse.java:15-21` 的 `trend` 明确为 `List<TrendDataPoint>`。`ThreatQueryService.java:285-312` 对空时间桶也会生成完整字段并填入 0；`558-584` 对数据库查询结果进行转换。因此无需修改后端字段来迁就前端错误类型。

## 5. 详细修复步骤

### 5.1 新建准确的 API 传输类型

1. 在 `frontend/src/types/index.ts` 新增专用类型，建议命名为 `ThreatTrendPoint` 或 `ThreatTrendDataPoint`，避免与后端同名时语义不清。
2. 字段与后端 DTO 一一对应：`timestamp`、`count`、`averageScore`、`maxScore`、`criticalCount`、`highCount`、`mediumCount`。
3. `timestamp` 在 JSON 中声明为 ISO 时间字符串；`count` 声明为数值。
4. 后端构建逻辑会为当前查询结果和补零桶填写所有统计字段，前端可按实际序列化契约声明必填；如需兼容历史后端，应在服务边界建立显式兼容适配器，而不是把正式类型改成任意字段并集。
5. 保留 `ChartDataPoint` 作为已经完成展示转换后的图表类型，不把 API 字段继续塞入它。

### 5.2 统一所有接口返回类型

1. 把 `OverviewSnapshot.trend` 改为新的趋势 API 类型数组。
2. 把 `getThreatTrend` 和 `getTenantTrend` 的请求泛型及 Promise 返回类型同步改为新类型。
3. 全局搜索 `ChartDataPoint`，确认只有图表状态、图表组件或转换后的数据继续使用它。
4. 检查趋势接口的其他调用者；每个调用者必须在自己的展示边界明确映射，不得依赖旧的 `time/value` 假设。

### 5.3 在 Overview 建立单一、强类型映射

1. 删除 `(item: any)`，让 `trend` 的类型自动推导为新的趋势 DTO。
2. 时间只从 `item.timestamp` 读取，并继续根据 24 小时/7 天/30 天范围格式化。
3. 图表值只从 `item.count` 读取；不再使用 `item.value` 回退。
4. 保留 `category` 作为前端本地化展示字段，它不属于后端 DTO。
5. 建议把映射提取为小型纯函数，以便直接单元测试 0 值、时间格式和不同趋势范围。
6. 若确实必须兼容一个仍返回 `time/value` 的旧部署版本，应在 `threatService` 中增加有版本说明的规范化函数，并记录移除期限；页面不得继续接收联合形状或 `any`。

### 5.4 让 Fixture 完全模拟真实响应

1. 删除 `OverviewTrendPoint = ChartDataPoint & { timestamp: string }` 临时交叉类型。
2. 把快照 Fixture 改为 `timestamp/count` 及真实 DTO 要求的统计字段，不再生成 `time/value`。
3. 直接使用 `satisfies OverviewSnapshot` 校验 Fixture，无需额外交叉类型。
4. 同步检查客户趋势和租户趋势路由 Mock，确保它们也返回同一 DTO 结构。
5. 增加负向契约测试或类型断言，避免后续有人再次给 API Fixture 添加 `time/value`。

### 5.5 补充映射与集成验证

1. 单元测试 `timestamp/count` 正确转换为 `time/value`。
2. 验证 `count: 0` 保持 0，不能被 `||` 误判为空值。
3. 验证空趋势数组生成空图表而不抛错。
4. 验证 24 小时、7 天、30 天三种时间标签格式。
5. E2E 使用真实字段 Fixture 验证 Overview 趋势图和统计卡正常渲染。

## 6. 潜在影响与规避方式

- 修正服务返回类型后，任何把趋势结果直接当作 `ChartDataPoint` 的隐藏调用者会出现编译错误；这些错误应逐一在展示边界转换，不能用 `as` 或 `any` 压掉。
- 移除 `item.value` 回退后，错误或旧版响应会更早暴露；若项目明确需要兼容旧部署，应在服务层进行版本化适配并记录告警。
- Fixture 改为真实契约可能暴露此前测试未覆盖的页面错误，这是修复价值，不应恢复双字段 Mock。
- 后端统计字段当前均有补零逻辑，但数据库异常数据仍可能导致转换失败；这是后端数据完整性问题，不应通过前端 DTO 可选化全部字段来掩盖。
- 本问题不改变后端接口路径、参数、数据库查询、趋势计算、租户权限或图表视觉设计。

## 7. 验证方法与验收标准

### 7.1 静态与类型验证

1. `npm.cmd run lint`
2. `npx.cmd tsc --noEmit`
3. 执行项目现有 E2E 类型检查命令。
4. `rg -n "item: any|item\.value|OverviewTrendPoint" frontend/src/pages/Overview frontend/e2e/helpers/apiFixtures.ts` 不再命中本问题中的临时兼容代码。
5. `rg -n "Promise<ChartDataPoint\[\]>|get<ChartDataPoint\[\]>" frontend/src/services` 不再用于后端趋势 DTO。

### 7.2 契约验证

- 直接请求 Overview 快照、客户趋势和租户趋势接口，确认响应字段与新前端类型一致。
- 对比 `TrendDataPoint.java`、前端 API 类型和 Fixture，字段名及数值含义一一对应。
- 验证 `generatedAt` 与 `trend[].timestamp` 都以可解析 ISO 时间字符串到达前端。
- 验证空时间桶返回 `count: 0`，图表仍连续显示而不是丢点。

### 7.3 页面回归

- 24 小时、7 天、30 天趋势范围均正常显示。
- 单客户、租户汇总和全部客户范围均正常加载。
- 空数据、只有一个数据点、全部为 0、多数据点情况下图表不报错。
- 快速切换数据范围时仍遵守现有请求代次保护，不显示旧请求结果。
- 接口失败时保留现有错误态，不因映射函数抛出未处理异常。

### 7.4 通过标准

- API DTO 与图表展示模型彻底分离。
- Overview 不再使用 `any` 或 `count/value` 双字段回退。
- E2E Fixture 只包含后端真实字段并通过 `OverviewSnapshot` 类型校验。
- 三个趋势响应入口使用同一个准确的前端 DTO 类型。
- 类型检查、相关单元测试和 Overview E2E 全部通过，且无新增兼容白名单。

## 8. 本阶段结论

后端趋势 DTO 已经明确，问题完全位于前端类型分层和测试 Fixture：API 传输类型被误写成图表展示类型，随后用 `any`、回退读取和双字段 Mock 掩盖。建议新增准确的趋势 DTO 类型，在 Overview 的单一边界转换为 `ChartDataPoint`，并让服务与 Fixture 共同遵守真实契约。当前仅形成方案，尚未修改任何源码、接口或测试。
