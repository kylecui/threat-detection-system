## 2. 问题描述

`frontend/e2e/readiness.spec.ts` 中的负向场景用于验证：当 Scope 请求永久不返回时，公共 helper 应报告“Scope / login bootstrap 未初始化”，而不是给出“找不到元素”的模糊错误。

但当前用例在调用诊断 helper 前，先直接执行：

```ts
await page.goto("/overview");
await expect(page.locator(".tds-shell")).toHaveAttribute("data-app-ready", "false");
```

该 `toHaveAttribute` 没有显式 timeout，使用 Playwright 默认 5 秒。Ubuntu 真实 4-worker 运行中，页面的懒路由加载、React 壳层挂载和认证恢复偶尔超过这 5 秒，导致用例提前以 `.tds-shell element(s) not found` 失败，后续真正要验证的 `waitForAppReady(page, { timeout: 4_000 })` 根本没有执行。

该问题在两个独立运行中复现：

- 全量 E2E：205/207，通过之外的两项之一即本用例；
- `readiness.spec.ts --workers=4 --repeat-each=3`：17/18，本用例再次失败一次。

失败截图在断言结束后已能显示 Overview 壳层，进一步说明这是断言窗口和挂载时机之间的竞争，而不是页面永久无法挂载。

## 3. 根本原因

### 3.1 壳层“已挂载”和应用“已就绪”是两个不同状态

`frontend/e2e/helpers/ready.ts:51-56` 的 `appIsReady` 要求：

1. 全局 Suspense 已退出；
2. 根节点已存在；
3. `data-app-ready=true`；
4. `data-route-path` 与当前 URL 一致。

本负向场景故意让 Scope 永远不完成，因此应用永远不会满足第 3 条。直接调用完整 `waitForAppReady` 来等待壳层，会把测试设计成必然超时；但完全绕过 helper 又留下了默认 5 秒竞争。项目缺少一个语义介于两者之间的“壳层已经挂载且路由已提交，但不要求业务初始化完成”公共等待。

### 3.2 默认 5 秒与项目既有冷启动预算不一致

`frontend/e2e/helpers/ready.ts:20` 已把应用级冷启动预算统一为 `APP_READY_TIMEOUT = 20_000`。`frontend/playwright.config.ts` 没有配置全局 `expect.timeout`，所以第 28 行仍使用 Playwright 默认 5 秒。也就是说，同一项目中普通业务用例允许 20 秒完成壳层初始化，而 readiness 契约自己的负向用例只允许 5 秒完成壳层挂载。

### 3.3 `page.goto()` 只完成导航，不保证懒路由和 React 壳层已提交

项目使用 Vite 开发服务器、React lazy 路由、认证恢复和 Scope 初始化。`page.goto()` 返回时只能说明导航生命周期达到默认等待条件，不代表 `.tds-shell` 已经挂载。全局预热能降低概率，但不能代替每个测试自己的状态同步；4 workers 共享 CPU、内存和 Vite 转换资源时仍可能越过 5 秒边界。

### 3.4 静态合同允许 readiness 用例裸用 `page.goto`

`tests/test_e2e_stability_contracts.py:79-88` 明确允许 `readiness.spec.ts` 和 `overview-trend.spec.ts` 使用原始 `page.goto`，但没有进一步要求 readiness 负向用例必须先通过一个有界的“壳层挂载”契约。因此现有合同能阻止普通 spec 绕过 `gotoReady`，却无法阻止本问题再次出现。

### 3.5 资源余量是放大因素，不是直接根因

Ubuntu 全量运行前可用内存约 3163 MiB，容器峰值达到 2911 MiB；`scripts/testing/run_frontend_e2e_ubuntu.sh:34-36, 103-108` 的默认门槛仍是 3 GiB。较小余量会放大冷启动延迟，但即使提高内存，测试也不应依赖默认 5 秒的隐式等待。应先修正状态契约，再依据连续绿色运行的峰值决定资源门槛。

## 5. 详细修复方案

### 5.1 在公共 helper 中增加“根节点已挂载”契约

建议在 `frontend/e2e/helpers/ready.ts` 新增并导出 `waitForAppRootMounted`（名称也可为 `waitForAppShellMounted`），复用现有 `readAppState` 和 `describeAppState`，而不是在 spec 中复制 DOM 轮询。

该 helper 的就绪条件应为：

```ts
!!state
  && !state.globalLoading
  && state.roots.some((root) => root.route === state.path)
```

关键语义：

- 要求全局 Suspense 已退出；
- 要求当前路由对应的根节点已经提交；
- **不要求** `root.ready === "true"`，允许负向场景中的 `data-app-ready=false`；
- 默认使用 `APP_READY_TIMEOUT`，不引入新的随意时间常量；
- 超时信息应调用 `describeAppState`，保留“仍在导航 / Suspense / 无壳层 / 路由未提交”等分层诊断。

可以复用 `waitForStable`，但该挂载等待不需要额外 1 秒稳定窗口；应明确传入 `stableMs: 0`，避免把 20 秒预算额外消耗在与目标无关的稳定期。

### 5.2 修改负向用例的同步顺序

`frontend/e2e/readiness.spec.ts:21-36` 应调整为：

1. 注册永不返回的 Scope 路由；
2. 执行 `page.goto('/overview')`；
3. 调用 `waitForAppRootMounted(page)`；
4. 在已确认壳层存在后，断言当前路由为 `/overview` 且 `data-app-ready=false`；
5. 调用原有 `waitForAppReady(page, { timeout: 4_000 })`，继续验证它准确报告 Scope 层未就绪；
6. 在 `finally` 中 abort 所有 pending route，确保前置断言失败时也不会遗留悬挂请求。

属性断言可以使用较短的显式局部 timeout，因为根节点已经由公共 helper 确认存在；不得再次依赖默认值。

### 5.3 补充静态合同

在 `tests/test_e2e_stability_contracts.py` 增加合同，至少验证：

- `ready.ts` 导出新的根节点挂载 helper；
- helper 使用 `APP_READY_TIMEOUT`、`describeAppState`，且不要求 `data-app-ready=true`；
- readiness 负向用例在 `page.goto` 之后、属性断言之前调用该 helper；
- pending routes 使用 `finally` 清理；
- 不新增 `waitForTimeout`、全局 expect timeout、retry 或 `test.slow()`。

合同不应只搜索函数名，还应检查调用顺序，避免存在 helper 但实际仍先执行默认 5 秒断言。

### 5.4 校准 Ubuntu 资源门槛，但不与同步修复混为一谈

代码同步修复完成后，使用相同 4-worker 参数记录至少两轮完整运行的 `host_mem_available_kib` 和 `container_memory_peak_mib`：

- 若峰值持续接近 3 GiB，应将 `TDS_E2E_MIN_MEM_GB` 默认值提高到 4，或按 worker 数计算门槛；
- 若 3 GiB 环境仍能连续两轮稳定通过，可保留当前门槛，但在文档中记录实测余量；
- 不得通过降低到单 worker、增加 retry 或全局放大 timeout 代替状态同步。

### 5.5 修正关闭记录的证据口径

完成修复后，应在 `INTERACTION-011` 的后续复查或关闭记录中区分：

- 本地静态/单元测试；
- Ubuntu 真实浏览器结果；
- 实际执行项和环境跳过项；
- 单次通过与连续两个清洁轮次通过。

历史 `02_修复结果.md` 不应静默删除或重写；应追加新的复验记录说明此前 `207/207` 和 `74/74` 的环境边界。

## 6. 禁止采用的表面修复

- 把全局 `expect.timeout` 调大后直接关闭问题；
- 在第 28 行仅填入一个更大的数字，而不建立可复用的壳层挂载语义；
- 使用 `waitForTimeout` 等固定 sleep；
- 给失败用例增加 retry；
- 把整个回归降为单 worker；
- 删除负向用例或改成只检查任意错误文本；
- 在负向场景中调用要求 `data-app-ready=true` 的完整 `waitForAppReady` 作为前置等待。

## 7. 潜在影响与风险

1. **helper 条件过宽**：如果只检查 `.tds-shell` 数量，不检查 `data-route-path`，可能在路由切换期间错误接受旧壳层。
2. **helper 条件过严**：如果复用 `appIsReady`，负向场景会永远超时，无法验证真正的诊断文本。
3. **稳定窗口误用**：默认 1 秒稳定期会增加每个负向场景耗时；挂载只需一次有界确认。
4. **路由清理遗漏**：未在 `finally` abort pending route 会让失败后的页面保持悬挂，增加报告生成和 teardown 的不确定性。
5. **资源门槛过度调整**：仅凭一次 2911 MiB 峰值直接大幅提高门槛可能降低可用性，应以两个完整轮次数据决定。
6. **生产影响**：建议修改仅涉及 E2E helper、E2E spec、合同测试和测试文档，不应修改业务页面、API 或部署行为。

## 9. 建议结论

该问题应作为独立的测试同步缺陷修复。首选方案是建立可复用、可诊断、允许 `data-app-ready=false` 的“根节点已挂载”契约，并让负向用例在 `finally` 中可靠清理悬挂请求。只有 Ubuntu 4-worker 连续两个清洁轮次全部通过后，才能同时关闭本问题和 `INTERACTION-011` 的相关遗留项。
