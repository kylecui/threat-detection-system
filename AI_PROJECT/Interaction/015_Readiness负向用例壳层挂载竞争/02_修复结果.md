## 2. 根因确认

1. **复现**：我在本地复现了与 Ubuntu 完全相同的失败。条件是修复前代码、模拟冷启动（每个懒加载 chunk 首次请求延迟 7 秒）、不预热、只运行该用例。失败信息为 `toHaveAttribute … locator('.tds-shell') with timeout 5000ms … element(s) not found`，位置在原第 28 行，后面的诊断断言没有执行。
2. **原因**与第一阶段分析一致：
   - “壳层已挂载”和“应用已就绪”是两个不同状态，但项目只有后者的公共等待；
   - 负向用例的前置断言因此只能直接写 locator 断言，落入 Playwright 默认的 5 秒窗口，比项目统一的 20 秒冷启动预算短得多。
3. **生产代码无缺陷**：页面在 Scope 永不返回的情况下仍会挂载壳层（`data-app-ready=false`），只是冷启动时晚于 5 秒。修复后的同一场景可以通过（见 4.2）。

## 3. 修复内容

### 3.1 公共 helper：“根节点已挂载”契约（方案 5.1）

在 `frontend/e2e/helpers/ready.ts` 中新增两个导出：

- **`isAppRootMounted(state)`**，判定条件为：
  - 全局 Suspense 已退出（`!state.globalLoading`）；
  - 存在 `data-route-path` 等于当前 URL 路径的根节点；
  - **不要求** `data-app-ready="true"`。
- **`waitForAppRootMounted(page, { timeout })`**：
  - 复用已有的 `readAppState`（页面状态采样）和 `waitForStable`（轮询等待），不在 spec 中重复写 DOM 轮询；
  - 默认使用 `APP_READY_TIMEOUT`（20 秒），没有引入新的时间常量；
  - `stableMs: 0`：确认一次即可返回，不额外消耗 1 秒稳定窗口；
  - 超时信息形如 `App root mount not ready within 20000ms: <层级>`，层级沿用 `describeAppState`：导航中、全局 Suspense、无根节点。
  - 因为这个等待本来就不关心初始化，当已有根节点但路由不匹配时，直接报告 `route not committed: URL path …, rendered …`，不会误报为“Scope 未初始化”。
- `AppState` 类型改为导出，供 `isAppRootMounted` 的签名和单元断言使用。

### 3.2 负向用例的同步顺序（方案 5.2）

`frontend/e2e/readiness.spec.ts`：“a Scope that never initialises…”

1. 注册永不应答的 Scope 路由（与原来相同）；
2. 进入 `try`，执行 `page.goto('/overview')`；
3. 调用 **`waitForAppRootMounted(page)`**，在 20 秒冷启动预算内等待壳层挂载；
4. 壳层已确认存在后，用显式的 `ATTRIBUTE_TIMEOUT = 1_000` 断言：
   - `data-route-path="/overview"`；
   - `data-app-ready="false"`；
5. 原有断言不变：`waitForAppReady(page, { timeout: 4_000 })` 必须报告 `Scope / login bootstrap not initialised (data-app-ready=false)`，且包含当前 URL；
6. 在 **`finally`** 中 abort 全部挂起的 Scope 请求。即使前面任何一步失败，也不会把悬挂请求留到 teardown 和报告生成阶段。

### 3.3 helper 自身的验证用例

新增用例“the root-mount wait accepts an uninitialised root and names the missing layer”：

- 在 `about:blank` 上用 `page.setContent` 放置静态 DOM，不依赖应用和服务器，结果确定；
- 验证四种情况：
  - 根节点 `data-app-ready=false` 但路由已匹配 → 通过；
  - 有全局 Loading → 报告 `global Suspense fallback`；
  - 没有根节点 → 报告 `no app shell…`；
  - 路由不匹配 → 报告 `route not committed…`；
- 另外对 `isAppRootMounted` 直接断言四种状态，确保条件既不过宽（接受旧路由的壳层），也不过严（要求 `ready=true`）。

### 3.4 静态合同（方案 5.3）

`tests/test_e2e_stability_contracts.py` 的 `ReadinessContract` 新增 2 项：

- **`test_root_mount_helper_does_not_require_initialisation`**：
  - 判定函数包含 `!state.globalLoading` 和 `root.route === state.path`，且不出现 `"true"`；
  - 等待函数使用 `APP_READY_TIMEOUT`、`describeAppState`、`stableMs: 0`。
- **`test_negative_scope_test_waits_for_the_mount_first`**（检查顺序，不只是检查函数名是否出现）：
  - 9 个关键步骤必须按此顺序出现：注册路由 → `try` → `goto` → 挂载等待 → 两个带显式 timeout 的属性断言 → 4 秒诊断 → `finally` → `abort`；
  - `abort` 只能出现在 `finally` 中；
  - 该用例内每个 locator 断言都必须写明 `timeout`；
  - `readiness.spec.ts` 中每次裸 `page.goto` 之后（允许中间夹注释），下一条语句必须是 `waitForAppRootMounted` 或 `waitForAppReady`；
  - 禁止 `waitForTimeout`、`test.slow(`、`retries`；
  - `playwright.config.ts` 不得配置全局 `expect` 块，也不得配置非零 retries。

## 6. 未解决问题与注意事项（关闭前必须完成）

1. **Ubuntu 定向验证**（方案 8.2），要求 35/35 通过（新增 1 个用例，原 30/30 变为 35/35）、0 retry、0 skip，日志中不再出现 `.tds-shell element(s) not found`：

   ```bash
   scripts/testing/run_frontend_e2e_ubuntu.sh e2e/readiness.spec.ts --workers=4 --repeat-each=5
   ```

2. **两个全新容器轮次**（方案 8.3，按 011 原口径）：每轮依次执行 Overview 定向重复、四组关键 spec 组合、全量 E2E `--workers=4`。每轮使用空的 npm 缓存，例如 `TDS_E2E_NPM_CACHE=$(mktemp -d)`。保存 `results.json`、`console.log`、`run-info.txt` 和 `memory-samples.txt`。
3. **内存门槛判定**：两轮结束后，取两轮 `container_memory_peak_mib` 的较大值：
   - 如果超过约 2.7 GiB（也就是 3 GiB 门槛下余量不足 10%），把 `TDS_E2E_MIN_MEM_GB` 的默认值提高到 4；
   - 否则保留 3 GiB，并在复查报告中记录实测余量。
   - 本次 Ubuntu 复查的单次峰值为 2911 MiB，已经接近这个界限，所以提高到 4 的可能性较大。但按方案要求，应以两轮数据为准。
4. 以后写需要页面**保持未就绪**的负向用例时，用 `waitForAppRootMounted`，不要直接写 locator 断言；需要页面就绪的用例继续用 `gotoReady`。
