## 2. 修复结果总结

### 2.1 应用级就绪契约（步骤一）

App 壳层 `.tds-shell` 增加两个机器可读、对用户与读屏软件都不可见的属性：

- `data-app-ready`：取自 `ScopeContext` 真实的 `initialized` 状态；
- `data-route-path`：当前**已提交渲染**的路由。

`.tds-shell` 存在，说明根 `Suspense` 已退出、主布局已挂载。路由更新在 transition 中执行，懒加载页面渲染完成前，`data-route-path` 仍停在旧路由，所以“属性等于当前 URL”即可证明页面模块已经加载并提交。

登录页另行定义就绪语义：

- `.tds-login` 的 `data-app-ready` 在 bootstrap 状态检查结束后为 `true`，检查成功或失败都算结束；
- `data-route-path="/login"`。

测试专用页面 `ConfigCascadingHarness` 也提供同样的标记（没有 Scope，挂载即就绪）。

认证本身从 localStorage 同步恢复，不存在异步恢复阶段。因此就绪条件为：全局 Loading 已退出、壳层已挂载、Scope 已初始化、当前路由已提交。所有标记都来自真实应用状态，测试不注入、不伪造。

### 2.2 公共 E2E 就绪 helper（步骤二、三）

新增 `frontend/e2e/helpers/ready.ts`：

| helper | 作用 |
| --- | --- |
| `waitForAppReady(page)` | 等待 `.tds-app-loading` 消失，且存在 `data-app-ready="true"`、`data-route-path` 等于当前 URL 路径的根节点；上限 20 秒 |
| `gotoReady(page, url)` | `page.goto` 加上 `waitForAppReady`；`setAuthState()` 仍只负责注入状态，不隐式导航 |
| `waitForOverviewReady(page)` | 应用就绪后，等待 Overview 骨架屏（`aria-busy`）退出、已加载分支出现，并稳定 1 秒；数据、空数据和错误三种结果都算就绪 |
| `waitForTableReady(locator, { mode })` | 从 `table-layout.spec.ts` 提取：表格数量与行数达标、无 spinning、连续稳定 1 秒；支持 `"data"` 和 `"empty"` 两种模式，不会误伤合法的空数据 |
| `waitForStable()` | 上述“条件连续成立一段时间”的通用实现 |

超时时报错会指出**具体未就绪的层级**，并附带当前 URL、页面中 spinning 和 `aria-busy` 的数量。例如：

```text
App not ready within 20000ms: global Suspense fallback .tds-app-loading still shown (lazy route chunk / bootstrap); url=…/investigate/intel; spinning=1; aria-busy=1
App not ready within 4000ms: Scope / login bootstrap not initialised (data-app-ready=false); url=…/overview; …
```

不再只报“locator 不存在”。

### 2.3 隔离冷编译与业务断言（步骤四）

新增 `frontend/e2e/global-setup.ts`，并在 `playwright.config.ts` 中注册为 `globalSetup`。它在 Web Server 启动之后、任何用例开始之前执行：

- 在**独立的浏览器上下文**中依次访问全部懒路由，共 17 个：14 个业务路由、登录页、404 页、ConfigCascading 测试页；每个路由都等待真实的应用就绪契约。这个上下文与用例不共享任何存储。
- 首轮单路由上限 120 秒；随后用正常的 20 秒上限再走一遍，证明已经预热。
- 打印每个路由的就绪耗时，以及容器内 CPU、MemAvailable、`/dev/shm`。
- 任一路由无法就绪时直接失败，并报告具体层级，而不是让大量用例随机超时。
- 设置 `E2E_SKIP_WARMUP=1` 可跳过（例如单独调试某个 spec）。

预热只是附加保障，所有 spec 仍然通过 2.2 的契约同步（步骤四第 4 点）。

**没有采用方案首选的“生产构建 + Vite preview”**，原因：

1. 生产构建使用 terser，并开启 `drop_console`，加载生产版 React。这样一来，012 依赖的 StrictMode 告警和控制台错误门禁会被一并关掉，E2E 失去这部分检查能力。
2. 若改为“development 模式的构建 + preview”，需要额外的构建配置，并且要把测试专用页面纳入构建入口，而本工作区无法运行 Vite，没法验证（项目安装的 esbuild/rollup 是 Windows 原生二进制）。

方案对“保留 dev server”的四项要求都已满足：

- 预热全部懒路由；
- 预热结束后才开始业务计时；
- 预热不复用测试状态，也不污染存储；
- 保留就绪契约。

### 2.4 用例修改

| 用例（Ubuntu 失败项） | 修改 |
| --- | --- |
| 13 个 spec 中全部 `page.goto` / `page.reload` | 改为 `gotoReady` / `reload` 后接 `waitForAppReady`，共 59 处导航、3 处 reload。`overview-trend` 与 `readiness` 两个 spec 显式使用 `page.goto` 加就绪等待 |
| 登出 | 回到登录页后再等待登录页就绪 |
| 分组威胁排序 | 先 `waitForTableReady`，再断言行和排序 |
| 空 Overview、HTTP 失败、网络超时 | 先 `waitForOverviewReady`，再断言空状态或错误提示 |
| 主路由可访问 | 原来在一个 30 秒用例中连续整页加载 14 次，现拆成 14 个独立用例，每个都断言 URL 和 `data-route-path` |
| 侧栏固定、菜单高亮、i18n 切换、CUSTOMER_USER 标题 | 通过 `gotoReady` 等待应用壳层就绪后再操作 |
| Overview 390 移动端（`overview.spec`、`table-layout` 的 overview 展示面） | 等待骨架退出后再断言移动列表。`tableSurfaces` 新增 `ready` 钩子，overview 展示面使用 `waitForOverviewReady`，卡片模式和表格模式都会执行 |
| Top 攻击者排序、设备抽屉 | `rows()` 改为基于 `waitForTableReady`；排序用例要求 Overview 就绪且表格至少 2 行 |
| 设备数据流弹窗（组合回归失败项） | 打开弹窗后在弹窗内等待表格行稳定 |
| `overview-trend.spec.ts` | 在导航前就开始记录快照响应，因此不会漏掉；15 秒业务预算从“应用就绪”之后（或点击之后）才开始计时，冷编译和 Scope 初始化由 `waitForAppReady` 与预热负责。仍要求路径、`hours`、2xx 三项都匹配 |

所有相关用例都没有使用固定 sleep，也没有修改全局超时、重试或并发数。

## 5. 与方案的差异

| 方案 | 实际 | 原因 |
| --- | --- | --- |
| 步骤四首选“生产构建 + Vite preview” | 保留 dev server，增加受控预热 | 见 2.3。生产构建会去掉 console 与 React 开发版告警，削弱 012 的门禁；本环境也无法运行 Vite 来验证构建配置 |
