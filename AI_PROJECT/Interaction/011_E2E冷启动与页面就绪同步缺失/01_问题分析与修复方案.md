# INTERACTION-011：E2E 冷启动与页面就绪同步缺失

## 1. 文档状态

- 阶段：问题分析与修复方案。
- 结论：已定位根因，**本阶段未修改业务源码、测试源码或运行脚本**。
- 依据：Ubuntu 真实 Playwright 1.59.1 三组报告、失败截图/错误上下文，以及当前前端源码交叉检查。
- 关联记录：`INTERACTION-010/04_Ubuntu真实Playwright复验报告.md`。

## 2. 问题描述

Ubuntu 4-worker 真实浏览器回归中，以下现象反复出现：

1. `overview-trend.spec.ts` 单独并发重复执行时 9 项中 4 项失败，失败均为首个 `hours=24` snapshot 响应超过 15 秒；同一测试又有 5 次通过。
2. 四个关键 spec 组合执行时，Overview 三项全部超时，设备数据流、Top 攻击者和设备抽屉又分别出现“断言时无行、稍后的失败截图已有数据”或“仍在骨架屏”的现象。
3. 完整套件的 44 个失败中，有 14 个属于同一类启动/页面数据就绪竞争，涉及全局 Loading、Scope 初始化、移动端 Overview 卡片、表格首行、工作区按钮、菜单高亮和 RBAC 页面标题。
4. 完整套件运行到 `overview-trend.spec.ts` 时该 spec 三项反而全部通过，说明依赖模块被其他用例预热后，固定时间窗口内可以完成；测试本身并不具备冷启动独立性。

本问题不是 Playwright 镜像、Chromium 启动、接口 DTO 或移动端卡片结构缺失。镜像已经能够正常运行；Overview 两组移动卡片 DOM 位于已加载分支中，失败时只是仍处于骨架分支。

## 3. 根本原因

### 3.1 Web Server “可访问”不等于业务应用“已就绪”

`playwright.config.ts` 只等待 `http://localhost:3000` 可访问，而测试服务器使用 `npm run dev`。Vite 根地址开始响应后，React 懒加载路由仍可能在首次访问时编译。

`App.tsx` 将 Overview、告警、威胁、客户设备、配置等页面全部通过 `React.lazy()` 加载，并在整个路由树外使用统一 `Suspense`。因此冷访问任何尚未编译的路由都会显示 `.tds-app-loading`，但测试已开始计算响应或断言超时。

### 3.2 Scope 初始化是第二层异步门槛

`ScopeProvider` 初始 `initialized=false`，随后异步恢复租户/客户范围并在结束时设为 `true`。Overview 只有在 `initialized=true` 后才执行 `loadData()`。现有测试 helper 负责注入认证和 API mock，但没有等待 Scope 完成的公共契约。

因此当前实际链路是：

`Vite 地址可访问 → React 懒加载编译 → Auth 恢复 → Scope 初始化 → 页面请求 → React 状态提交 → 表格/卡片渲染`。

多数测试只等待第一步或某一个请求，随后立即查 DOM，无法证明后续步骤已完成。

### 3.3 固定 15 秒把冷编译时间算进了业务响应时间

`overview-trend.spec.ts` 在 `page.goto('/overview')` 前注册 snapshot response，随后使用固定 15 秒等待。监听顺序本身正确，但计时范围包含懒模块编译、Auth/Scope 初始化和真正发出业务请求之前的全部时间。4 worker 同时冷启动且容器仅按 3 GiB 可用内存门槛运行时，容易在请求尚未发出前耗尽预算。

### 3.4 页面级断言缺少稳定就绪条件

- Overview 的 `loading` 分支只渲染骨架，不包含 `.tds-overview__mobile-list`；已加载分支始终包含两组移动列表。390px 用例在 `reload()` 后立即查找移动列表，默认等待窗口内页面仍可能在骨架分支。
- 表格交互用例在页面尚处于 loading/spinning 时查找首行或读取排序结果。
- 工作区、RBAC、i18n、菜单高亮元素在稳定 App Shell 中确实存在，但用例在全局 `Suspense` fallback 尚未退出时开始断言。

截图是在断言失败后采集的，截图中页面后来已加载不能反证断言时已就绪。

## 5. 详细修复步骤

### 步骤一：建立应用级就绪契约

1. 在稳定 App Shell 根节点提供机器可读、用户无感的就绪状态，例如 `data-app-ready`/`aria-busy`。
2. 就绪条件至少同时包含：全局 `Suspense` 已退出、认证恢复完成、Scope `initialized=true`、主布局已挂载。
3. 状态必须来自真实应用状态，不能由测试注入或固定延时伪造。
4. 登录页与受保护页面分别定义就绪语义，避免登出用例等待不存在的主布局。

### 步骤二：增加公共 E2E 等待 helper

1. 在 `frontend/e2e/helpers/` 增加 `waitForAppReady(page)`，等待 `.tds-app-loading` 消失和应用级就绪状态成立。
2. 增加 `waitForScopeReady(page)` 或把 Scope 条件合并到 `waitForAppReady()`，禁止各 spec 自行 `waitForTimeout()`。
3. helper 必须有明确上限，并在失败信息中输出当前 URL、全局 Loading、Scope、页面 busy/spinning 状态，便于区分真正卡死与慢启动。
4. `setAuthState()` 继续只负责注入状态；导航后的等待由明确 helper 执行，避免 helper 隐式导航造成请求监听顺序错误。

### 步骤三：建立页面级数据稳定契约

1. Overview：等待精确 snapshot 响应后，再等待 `.tds-overview[aria-busy='true']` 消失，并确认目标图表、空状态、表格或移动列表已经挂载。
2. 表格：提取 `table-layout.spec.ts` 现有逻辑为公共 `waitForTableReady()`；要求 spinning=0、预期表格数/行数成立，并连续稳定至少 1 秒。
3. 抽屉/弹窗：先等待容器可见，再等待其内部 loading 消失和预期行稳定，不能直接查 `.first()`。
4. i18n、RBAC、菜单动效：动作前先等待 App Shell，动作后等待目标工作区/语言/路由状态完成，再断言具体 UI。

### 步骤四：隔离开发服务器冷编译与业务断言

首选方案是在 Ubuntu/CI runner 中执行生产构建并使用 Vite preview 提供静态资源，使 Playwright 运行期间不发生按路由冷编译。API route mock 仍由浏览器层拦截，不受 preview 影响。

如确需保留 dev server：

1. 在测试正式开始前受控预热全部懒路由模块；
2. 预热结束后再启动业务响应计时；
3. 预热过程不得复用测试业务状态或污染本地存储；
4. 仍必须保留步骤一至三的就绪契约，不能仅依赖预热。

不建议只增加 15 秒超时、增加 retry 或降低 worker。这些手段只能降低暴露概率，不能消除错误同步模型。

### 步骤五：校准资源门槛和诊断信息

1. 记录容器实际 `MemAvailable`、CPU、`/dev/shm`、Vite/preview 启动耗时和首个页面 ready 耗时。
2. 根据两次干净容器的实测峰值决定最低内存，而不是继续使用恰好 3 GiB 的经验门槛。
3. 保留 4-worker 为验收目标；资源不足时应在 preflight 明确失败，不应让大量用例以随机超时形式失败。

## 6. 潜在影响

1. 切换到 build + preview 会增加测试前构建时间，但显著减少用例间的冷模块耦合。
2. 应用级 ready 标记若定义过宽，可能让测试过早继续；若定义过严，可能把不影响目标场景的后台轮询也当作阻塞条件。
3. 公共表格等待若只看“至少一行”，会误伤合法空数据场景；helper 必须支持“有数据”和“预期为空”两种模式。
4. 预热所有路由会增加启动耗时和内存，且可能掩盖真实 chunk 加载错误，因此优先推荐生产构建预览。
5. 不应通过关闭并发、全局放大超时或增加重试来获得表面通过，否则真正的状态竞争仍会保留。

## 7. 验证方法

1. 从全新的 Playwright 容器和空 npm 缓存启动，执行：
   - `e2e/overview-trend.spec.ts --workers=4 --repeat-each=3`
   - 四个关键 spec 组合 `--workers=4`
   - 完整套件 `--workers=4`
2. 三组均不得依赖 retry，Overview 定向 9/9 通过，完整套件不再出现全局 Loading、骨架屏、首行缺失或移动列表过早断言。
3. 再从第二个干净容器重复三组，确认结果与模块缓存无关。
4. 增加 helper 自身负向验证：故意让 Scope 永不完成时，错误信息必须明确指出 Scope/页面未就绪，而不是只报 locator 不存在。
5. 验证空数据、HTTP 错误、网络超时仍能进入各自业务状态，公共 ready helper 不得把合法错误页误判为“永远未就绪”。
6. 对 390px Overview 验证骨架退出后移动列表可见、桌面表格隐藏，并校验威胁分数、检测窗口等字段。

## 8. 验收标准

- 冷容器、4 worker、无重试情况下三组命令稳定通过两轮。
- 业务响应计时不再包含不可控的 Vite 路由冷编译。
- 所有相关 spec 通过公共应用级/页面级 ready 契约同步，不使用任意固定 sleep 兜底。
- 加载失败时报告能指出具体未就绪层级。
- 不改变现有认证、权限、Scope、API、页面功能和用户可见文案。
