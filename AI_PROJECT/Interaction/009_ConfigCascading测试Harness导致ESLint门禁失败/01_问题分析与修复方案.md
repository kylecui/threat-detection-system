## 2. 问题描述

当前执行以下标准命令时失败：

```bash
cd frontend
npm run lint
```

实际结果为 0 个 error、1 个 warning；由于 `frontend/package.json:17` 使用 `--max-warnings 0`，任何 warning 都会令命令返回退出码 1：

```text
e2e/harness/config-cascading.tsx:27:10
Fast refresh only works when a file has exports.
react-refresh/only-export-components
```

该结果已经在 Windows 和 `192.168.100.9` Ubuntu 24.04 x86_64 的 Node 22 干净依赖环境中分别复现，因此不是换行符、路径分隔符、Node 平台可选依赖或操作系统差异导致的问题。

ConfigCascading 目前按产品决策保留源码但不开放生产入口。为了继续验证该组件，E2E 使用独立 Vite Harness 页面；问题只发生在这个测试入口，但项目 lint 会扫描整个 `frontend`，所以仍会阻断正式质量门禁。

## 3. 复现步骤与证据

1. 在 `frontend` 执行干净依赖安装。
2. 执行 `npm run lint`。
3. ESLint 在 `frontend/e2e/harness/config-cascading.tsx:27` 报出一个 `react-refresh/only-export-components` warning。
4. 因 `--max-warnings 0`，lint 退出码为 1。
5. 同一源码在 Windows 与 Ubuntu 上结果一致。

关联证据：

- `AI_PROJECT/Interaction/007_配置级联查询区窄屏裁切/03_复查验收报告.md`
- `AI_PROJECT/records/tests/2026-10-28-release-3.1.37-interaction-review.md`

## 4. 根本原因

### 4.1 Harness 文件混合了组件定义与应用启动职责

`frontend/e2e/harness/config-cascading.tsx:27-51` 定义了本地 React 组件 `HarnessShell`，但没有导出；同一文件的 `53-61` 行又直接执行 `ReactDOM.createRoot(...).render(...)`。

因此该文件同时承担：

- React 组件实现；
- 测试应用 Provider 组装；
- 浏览器入口启动。

Fast Refresh 规则希望组件模块具有明确、可分析的组件导出边界。当前文件存在首字母大写的本地函数组件，却完全没有导出声明。

### 4.2 ESLint 规则准确命中了 `noExport` 分支

`frontend/.eslintrc.cjs:13-16` 将 `react-refresh/only-export-components` 配置为 warning。

当前安装的 `eslint-plugin-react-refresh` 规则实现会：

1. 将首字母大写的 `FunctionDeclaration` 识别为本地组件；
2. 在文件没有任何导出时进入 `noExport` 分支；
3. 对 `HarnessShell` 报出“file has exports”警告。

这证明根因是模块职责和导出结构，不是业务组件 `ConfigCascading`、响应式 CSS 或运行平台。

### 4.3 项目把 warning 作为失败处理

`frontend/package.json:17` 明确使用：

```text
eslint . --ext ts,tsx --report-unused-disable-directives --max-warnings 0
```

规则本身虽然是 `warn`，但项目的质量策略要求 warning 数量必须为 0，所以不能把它视为可忽略提示。

## 6. 详细修复方案

### 6.1 推荐方案：拆分组件模块和启动入口

新增测试专用组件文件，例如：

```text
frontend/e2e/harness/ConfigCascadingHarness.tsx
```

将下列内容从现有入口移动到新文件：

- `ConfigProvider`、中英文 locale、`useTranslation`；
- 全局及 Configuration CSS 引入；
- `useTheme`、`createAppTheme`；
- `ConfigCascading`；
- `CONFIGURATION_ACCENT`；
- `HarnessShell` JSX。

新文件只负责组件实现，并使用命名导出：

```tsx
export function HarnessShell() {
  // 保持现有主题、语言、DOM 壳层和 ConfigCascading JSX 不变
}
```

现有 `frontend/e2e/harness/config-cascading.tsx` 收敛为纯启动文件，只保留：

- React/ReactDOM；
- `ThemeProvider`；
- `AuthProvider`；
- 从新文件导入的 `HarnessShell`；
- `createRoot(...).render(...)`。

这样入口文件不再定义本地 React 组件，组件文件则只导出 React 组件，符合 Fast Refresh 的模块边界。

### 6.2 保持既有 Harness 契约

修复不得改变：

- `config-cascading.html` 的脚本入口路径；
- `/e2e/harness/config-cascading.html` URL；
- Provider 嵌套顺序 `ThemeProvider → AuthProvider → HarnessShell`；
- `.tds-shell > .tds-content > .tds-content__inner > .tds-route-stage` DOM 层级；
- `data-testid="config-cascading-harness"`；
- Configuration 工作区强调色；
- ConfigCascading 仍不进入生产路由的产品决策。

### 6.3 不建议的处理方式

以下方式不应作为正式修复：

1. 全局关闭 `react-refresh/only-export-components`；
2. 把 `--max-warnings 0` 从 lint 命令中删除；
3. 在整个 `e2e/**` 目录增加宽泛 ESLint ignore；
4. 用行内 `eslint-disable` 掩盖当前模块职责混合；
5. 修改 `node_modules` 中的规则实现。

仅把当前函数改为 `export function HarnessShell()`按现有规则实现大概率可以消除 `noExport`，但仍保留“组件实现和启动副作用同文件”的职责混合。可以作为最小验证手段，不建议作为最终结构。

## 7. 潜在影响与风险

### 7.1 正向影响

- 恢复 `npm run lint` 零 warning 门禁；
- 测试组件与启动逻辑边界清晰；
- 后续新增 Harness 组件时有可复用结构；
- 不修改生产路由、API、权限或业务组件。

### 7.2 可能风险

- Linux 文件名大小写敏感，新增文件名与 import 大小写必须完全一致；
- 移动 CSS 引入位置时如果遗漏，E2E 布局可能与生产样式不一致；
- Provider 层级改变会导致 `useTheme`、认证上下文或语言初始化失败；
- DOM 壳层改变会使 007 的响应式结论失效；
- 新文件如果导出非组件运行时值，仍可能触发同一规则的 `namedExport` 分支。

### 7.3 生产发布影响

`scripts/pack_release.py` 明确排除 `e2e`，所以该改动只影响开发/验收工具，不进入生产 tar.gz。仍应执行发布契约，防止未来打包清单变化造成测试文件误入包。
