**结论：第一次实际错误在 `install.sh:864`。** 默认 `rsync -a` 将“大小和时间相同”当成“内容相同”，跳过需要更新的文件。安装末尾打印旧版本只是最后暴露的现象，不是错误最先发生的位置。

统一归档时间戳是可复现打包策略，本身不是缺陷；缺陷是安装器的内容更新判定、目标校验和事务提交没有与该策略配套。

## 2. 问题描述与预期

### 2.1 用户可见现象

用户提供的关键输出为：

```text
[ OK ] Threat Detection System installation completed
  Version       : 3.1.32
  Install path  : /opt/threat-detection-system
...:/opt/threat-detection-system-3.1.39-linux-x86_64$
```

这不等于已证明所有服务仍运行 3.1.32，也不能仅凭新镜像标签断言全部文件已升级。当前实现可能形成“新环境和安装标记 + 部分旧文件”的混合安装树。

### 2.2 期望结果

- 只运行新包的 `sudo ./install.sh` 即可覆盖升级，不需要 purge；原业务数据、有效密钥和用户配置继续保留。
- 发布包中任一内容变化的受管文件都必须更新，即使文件长度、时间戳完全相同。
- 构建、启动和 `--no-start` 成功之前，必须验证目标内容及版本一致性。
- 发生异常时，文件回滚应恢复到实际升级前状态；恢复失败不得宣称成功或删除唯一恢复材料。
- 安装摘要、诊断及前端版本语义清晰。文件版本一致不等同于运行健康，运行健康也不等同于文件完整。

## 3. 完整调用链与第一次出错的位置

```text

  → install.sh 校验 SRC_ROOT 清单与源版本
  → 合并新运行环境、生成升级前快照
  → sync_release_tree / rsync -a          ← 第一次实质错误
       等长、同时间、不同内容的目标文件被跳过
  → 单独写入新 .env、新 .installed_version
  → 从可能混合的 TARGET_DIR 构建并启动
  → 健康/readiness/诊断自检未验证目标内容一致性
  → 关闭回滚、删除事务快照
  → print_summary 读取旧 TARGET_DIR/VERSION，显示 3.1.32
```

| 提交并丢弃事务快照 | `install.sh:1189-1190` | 已将 `INSTALL_ACTIVE=false` 并清理回滚目录；此后才发现显示异常，已晚于该事务的自动回滚窗口 |
| 表层版本显示 | `install.sh:1109-1117`，调用 `1191` | `print_summary` 从目标 `VERSION` 读取旧值，准确打印了错误目标状态；没有硬编码 `3.1.32` |

### 3.1 必须区分的两个“成功”

1. `rsync` 返回 0：只是按照其比较策略完成工作，不表示所有字节均与源一致。
2. 服务健康返回成功：说明服务能启动/接口可用，不表示构建输入、发布标记和诊断版本一致。

因此仅把打印语句改成 `$RELEASE_VERSION`，或只强制覆盖 `VERSION`，都会隐藏其他潜在漏复制文件，不能修复本问题。

## 4. 表层现象、直接诱因、根本原因和防线缺口

| 层级 | 定位 |
| --- | --- |
| 表层现象 | 3.1.39 安装成功摘要显示 3.1.32；诊断包可能同步显示旧版本 |
| 直接诱因 | `TARGET_DIR/VERSION` 没被新包替换，而摘要/诊断继续从该文件读取 |
| 根本原因 | 可复现发布包采用统一文件时间；升级同步却只按 size+mtime 决定是否更新，没有按内容判等。`VERSION` 两个版本均 7 bytes、mtime 均 0，内容不同仍被跳过 |
| 第一处状态分裂 | `install.sh:864` 跳过目标更新；随后 `868-869` 单独更新环境和标记，将新旧状态同时保留下来 |
| 防线缺失 | 只有源清单校验，缺少同步后目标受管内容校验；没有源版本/目标 VERSION/安装标记/运行环境版本联检 |
| 测试缺口 | `tests/test_release_contract.py:139-155` 对升级仅断言字符串、函数顺序及旧 rsync 命令存在；`38-65` 验证新包解压内容，不执行对旧树覆盖后的真实内容检查 |

没有发现生产安装逻辑中把套件版本硬编码为 `3.1.32`。也没有证据表明修改浏览器缓存、重新输入密码或 purge 能从根本上解决这个复制策略问题。

## 6. 同系问题及影响范围

### 6.1 版本显示与状态分裂

- `scripts/tdsdiag.sh:131-134、169-177`：读取同一目标 `VERSION`，写入 `diag-summary.txt/json`，会跟随旧文件错显。
- `install.sh:134-138、869`：新 `.installed_version` 优先于旧 `VERSION`，可能让下次识别显示“已安装 3.1.39”，但摘要仍显示 3.1.32。
- `frontend/src/App.tsx:750、903`、`frontend/src/pages/Configuration/GeneralConfig.tsx:99`：读取构建时 `VITE_APP_VERSION`，并不读取目标 `VERSION`。当前 `frontend/.env.production:4`、`docker/docker-compose.yml:745` 为 3.1.39，所以**可能**出现网页新版本/诊断旧版本，不是证明网页也必然显示错。
- `frontend/Dockerfile:47-49` 的参数和 Compose 镜像标签依赖运行配置；新标签只能证明命名，不证明构建输入完整。
- `.env.example` 若被跳过，第一次从新源包执行时运行 `.env` 仍可正确为新版本，因为准备环境使用新源模板，后续又单独安装；不能把模板旧值误说成此次 `.env` 一定旧了。
- 如果直接从受污染的安装目录重跑，旧 `VERSION` 与新 manifest 的不一致可能先在 `install.sh:183` 被拒绝，不能一概断言它一定会继续构建旧镜像。

### 6.2 回滚具有相同算法风险

`install.sh:759` 对已有目标树执行默认 `rsync -a --delete`，也可能跳过等长、同时间、内容不同的恢复项。**只修正正向同步会留下回滚缺口。**

`rollback_install:741-773` 没有恢复内容核验；`767` 的“previous installation was restored”不能证明逐文件恢复完成，随后 `773` 会清理事务快照。`cleanup_temp:776-779` 也会在事务非 active 的条件下清理快照，因此“失败时保留快照”的方案必须同时覆盖退出清理路径，不能只去掉某一行删除。

`prepare_rollback:701、706` 面向 `mktemp` 新目录，不是本例第一次误判；`backup_existing_install:880-882` 的备份一般也是新目录。不要将“所有 rsync 都必然漏文件”作为结论。

恢复验收应比对**实际升级前快照**，而不是强制信任旧安装的原 manifest：旧现场可能已经被本缺陷污染，原 manifest 未必代表实际升级前文件集合。

### 6.3 组件版本不应机械替换

`api-gateway/.../application.yml:190-194` 的组件 `info.app.version=1.0.0`、TIRE/ML FastAPI 的 `2.0.0` 与套件发布版本来源不同；Maven/npm、模型、协议、规则和插件版本也各有语义。它们不是当前 `3.1.32` 摘要的根因。本问题不把所有数字改成 3.1.39；需要展示时应明确标注“平台发布版本/组件 API 版本”。实际组件接口是否对外输出旧元数据尚未做生产验证。

## 8. 建议整改顺序与详细步骤

### P0：先建立会失败的复制回归

1. 用临时源/目标目录构造等长、mtime 同为 0、内容不同的 `VERSION` 和普通文件；先证明当前实现会漏更新。
2. 增加真实旧/新发布树覆盖用例，至少覆盖本次 3.1.32→新版本，以及旧 `.env.example` 的中间版本场景。
3. 测试只加载/调用被测同步和校验逻辑，systemctl、Docker、绝对系统安装路径均用受控桩或重定向隔离；禁止直接运行完整安装器来做普通单测。

### P1：修正升级与恢复的内容判等

1. 正向同步推荐采用 `rsync -a --checksum --delete --exclude='.env'`（或语义等效的内容比较），保留原归档属性、删除旧受管文件和 `.env` 保护边界。
2. 回滚恢复也采用内容判等；只修改正向同步不够。
3. 快照/备份复制面向新目录可保留原方式，但完成后记录可核验的实际快照内容；不把新目录复制误当成现有目录更新问题。
4. 不使用修改 mtime、只覆盖 `VERSION`、只改成功打印、强行同步所有依赖版本等绕过方案。

### P2：文件同步后立即增加可信目标校验

建议顺序为：

```text
校验源包并确定预期版本
  → 准备环境与实际旧状态快照
  → 内容比较同步生产文件
  → 用已验证源清单核验目标受管文件（失败即进入事务失败处理）
  → 核对目标 VERSION、目标模板与预期版本
  → 安装准备好的 .env，核对其 RELEASE_VERSION
  → 提交文件安装标记 .installed_version，联检元数据
  → no-start：仅报告文件安装完成；正常安装：构建/启动/运行验收
  → 再做最终版本一致性核验
  → 关闭事务并清理可清理的快照
  → 输出准确摘要
```

具体要求：

1. 同步前保存本次**已验证源清单**及预期版本。目标内容校验以该可信源清单为依据，同时检查目标 manifest 自身与源清单一致，不能只相信可能被跳过的旧目标清单。
2. 目标核验覆盖所有生产白名单文件，不只 `VERSION`；`.env`、安装生成标记、临时日志不是包内 manifest 文件，不应错误纳入源清单或要求其等于模板。
3. `.env` 内容继续使用现有生成器，保持凭据、配置和权限。元数据读取使用安全解析，不 `source` 不可信配置，也不输出完整 `.env`。
4. 校验失败时必须非零退出；不继续构建，不写“完成”标记，不走 `--no-start` 成功分支，不提前 `INSTALL_ACTIVE=false`。
5. 正常路径在 `1189` 之前完成最终一致性检查。不能等打印旧版本时才检查，那时事务快照已被清理。
6. `.installed_version` 保持“已安装文件版本”的既有语义，不将 `--no-start` 冒称为服务已升级；发布/运行验收状态在日志中分开表述。

### P3：完善回滚成功判定与恢复材料保留

1. 用受保护的事务目录保存实际升级前文件的校验信息和必要属性；旧树原 manifest 若有错误，记录该历史不一致，但不要将错误清单替代真实快照。
2. 按内容恢复目标与原有 unit，核对恢复文件集合与快照；验证完成再声明恢复成功。
3. 增加明确的事务/回滚结果状态。恢复失败时保留 `ROLLBACK_DIR` 及脱敏失败证据，退出清理函数必须遵守保留状态；返回非零并给出准确恢复路径，不能吞掉恢复命令错误。
4. 检查事务范围外复制的 `/usr/local/sbin/tdsdiag`：当前 `sync_release_tree:870` 更新该入口，但 `prepare_rollback` 仅备份目标树和 unit。下一阶段应将该入口的存在性/内容恢复纳入故障注入验证，避免失败升级后外部命令与旧树不一致；本阶段未操作该系统路径。
5. 文件快照不能回滚数据库变更，保持现有数据卷保护规则，不引入生产 `down -v` 或删除数据。数据库兼容性不由本文件恢复测试冒称已验证。

### P4：诊断与版本语义一致

1. 在 `tdsdiag --self-test` 提前返回前，采集目标 VERSION、安装标记、运行环境 RELEASE_VERSION，并计算一致性；新版规范安装出现不一致应报告明确失败。
2. 正常诊断报告分别给出各来源与 `version_consistency`，保留原 `version` 字段的兼容语义；不能从一个来源覆盖其他来源来“看上去一致”。
3. 兼容缺少安装标记的历史目录，明确标记 legacy/unknown 并给出可理解提示；不得在诊断中写文件“修好”版本。
4. 保持诊断只读和脱敏承诺。如只需运行环境版本，应仅解析允许键，不输出密码、JWT 或整个 Compose 环境。
5. 前端构建版本与套件版本仍走既有 Vite/Compose 参数；补验证，不为本问题重构 API 或修改组件/协议/模型版本。

### P5：发布与现场恢复

1. 修改完成后按项目规范完成前端/发布合同及新增升级、回滚回归；改动诊断自检时补兼容性测试。
2. 新包使用下一个未占用发布版本，不覆盖已交付 `outputs/v3.1.39/`，不在本分析阶段升版本或打包。
3. 受污染现场优先用通过验证的新安装器，从新包执行正常覆盖升级；不要求 purge、不清除数据。
4. 如需先核验现场，执行下一节只读命令，保存不一致文件清单。不要先手动改 `VERSION`、删除 `.installed_version` 或仅复制一个文件来掩盖证据。
5. 记录源码改动、测试命令、实际结果、版本和归档 SHA；构建、已安装、独立验收及生产发布状态分别记录。

## 9. 潜在影响与风险控制

- **内容比较开销**：同步会读取文件计算校验和，比 metadata 快捷检查多 I/O；应测量实际耗时，不以性能为由取消完整性保证。本阶段没有性能基准结论。
- **新校验可能发现历史残留**：对未完整升级的目标报错是合理行为；只有确认内容一致才允许成功，不得把检查降级为只打 warning。
- **凭据与数据保护**：正向 rsync 仍保护 `.env`；环境生成器继续保留有效密钥/用户设置。测试只比较虚构值是否保留，不打印秘密。命名数据卷不得由新校验清理。
- **恢复的可信依据**：应恢复到真实快照，不强行把受污染旧树“修成某个旧发布包”，否则可能改变升级前实际状态或覆盖用户设置。
- **事务与退出清理**：内容失败、环境安装失败、元数据错误、构建失败、恢复失败都必须走明确分支；尤其避免回滚失败后统一清理仍删除最后快照。
- **SRC_ROOT=TARGET_DIR**：源与目标相同路径时仍验证内容/元数据，不应触发自复制；如果源本已与其 manifest 不一致，应保持拒绝，不跳过源验证。
- **诊断兼容性**：新增字段保持旧字段可用，缺失/非法标记与真实不一致分开；不把组件 API 版本、npm/Maven 版本当套件发布版本比较。
- **生产运行边界**：静态内容、镜像标签和前端 mocks 都不能替代真实升级、数据库兼容及业务联通验收。

## 10. 验证计划与验收标准（下一阶段）

| 场景 | 必须满足的断言 |
| --- | --- |
| 全新安装到空目录 | 全部生产文件与可信源清单一致，生成环境与标记正确；首次管理员流程保持 |
| 等长同时间覆盖 | VERSION、普通源码/配置及模板内容均正确更新，不能只检查日志；覆盖 mtime=0 和非零相同时间 |
| 相同/不同版本重装、显式降级 | 所有受管内容收敛到执行包；保留原无额外确认的行为和原配置/数据规则 |
| 真实 3.1.32 与中间版本升级 | 覆盖 VERSION/pom.xml、VERSION/.env.example 两种组合；目标清单逐项通过 |
| 原目标已混合或被人工改过 | 新包能通过内容比较纠正受管文件；失败时保留证据，不将旧错误清单冒称可信快照 |
| 目标校验故障注入 | 漏复制、被篡改、缺失文件、替换目标 manifest 均在构建/成功标记之前被阻断 |
| `--no-start` | 同样执行内容与版本校验；不构建/启动服务；只报告文件安装完成 |
| 正向后构建/验收失败 | 使用内容恢复，目标与实际前态快照一致，凭据/unit/外部诊断入口正确恢复 |
| 恢复命令/验证失败 | 非零结果、明确报警，快照和证据不被 on_exit/cleanup 删除，不输出恢复成功 |
| 版本状态组合 | 源、目标 VERSION、安装标记、运行环境、前端构建版本一致；非法值/缺失值/legacy 单独测试 |
| 诊断自检/导出 | 版本不一致不可因健康接口 200 而通过；正常报告多来源字段正确、无凭据泄漏 |
| SOURCE=TARGET | 直接从目标运行时无自复制错误；受污染源被清单校验拒绝 |
| 数据与配置兼容 | 虚构旧密钥和自定义设置保留；无新增 purge、卷删除、认证或 API 行为变化 |
| 可复现打包与生产排除 | 统一 mtime 策略保留；研发/测试/证据不进生产包，新版本不覆盖既有归档 |

建议执行层次：先跑无需 Docker/systemd 的真实 rsync 隔离单测及静态合同；再在独立 Ubuntu 验证机跑真实新装、覆盖升级和故障回滚；最后按 `AI_PROJECT/RELEASE_PROCESS.md` 完成发布门禁和归档验证。**本阶段没有执行这些尚未实现的新测试，也没有重新运行会覆盖已交付同版本包的现有发布测试。**
