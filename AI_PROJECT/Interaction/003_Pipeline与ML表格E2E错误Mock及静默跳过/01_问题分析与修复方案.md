# 003 Pipeline 与 ML 表格 E2E 错误 Mock 及静默跳过——问题分析与修复方案

## 1. 文档信息

- 问题编号：`INTERACTION-003`
- 来源：`001_全局表格对齐与单行显示规范/03_复查验收报告.md` 的第二个遗留问题
- 优先级：P2
- 当前阶段：仅分析与制定方案，未修改源码
- 问题类型：E2E 数据契约、错误可见性、回归测试可信度

## 2. 问题描述

全局表格 Playwright 用例显示 26 项通过、7 项跳过。其中 Pipeline 和 ML 页面在 1440、1024 桌面/平板视口下本应渲染表格，却因为 Mock 返回错误数据结构而没有出现表格；测试随后通过通用 `test.skip` 静默跳过。

结果是：测试报告看起来没有失败，但这两个页面的核心表格实际上没有执行任何居中、单行、滚动和操作区断言。

## 3. 代码排查结果

### 3.1 错误 Mock 的位置

`frontend/e2e/helpers/auth.ts:95-135` 使用一个覆盖全部 `**/api/**` GET 请求的通用路由处理器：

- `auth.ts:107` 默认把任何未专门匹配的 GET 请求返回为 `EMPTY_PAGE`。
- `EMPTY_PAGE` 是分页对象 `{ content, totalElements, totalPages, size, number }`。
- `auth.ts:108-127` 只对评估、系统配置、LLM、插件等少量接口做了特定响应。
- `/api/v1/system/health` 和 `/api/v1/ml/**` 都没有对应分支，因此收到 HTTP 200 + 错误结构。

### 3.2 Pipeline 所需的数据契约

| 文件与位置 | 约束 |
| --- | --- |
| `frontend/src/services/system.ts:4-11` | `/api/v1/system/health` 返回 `PipelineHealthResponse` |
| `frontend/src/types/index.ts:770-786` | 必须包含 `status`、`timestamp`、`services`、`pipeline` |
| `frontend/src/pages/PipelineHealth/index.tsx:85-94` | HTTP 200 后直接写入 `health` 状态 |
| `frontend/src/pages/PipelineHealth/index.tsx:130-136` | 对 `health.services` 调用 `Object.entries` |
| `frontend/src/pages/PipelineHealth/index.tsx:435-467` | 桌面渲染服务状态表，移动端渲染记录卡片 |

`EMPTY_PAGE` 没有 `services`，但请求不会进入 `catch`，因为 HTTP 状态是 200。渲染阶段执行 `Object.entries(undefined)`，导致页面不能正常生成预期表格。

### 3.3 ML 所需的数据契约

| 文件与位置 | 约束 |
| --- | --- |
| `frontend/src/services/ml.ts:19-87` | 定义 7 个 ML GET 接口及各自响应类型 |
| `frontend/src/types/index.ts:473-541` | 模型、健康、缓冲区、漂移、影子评分、训练、数据就绪类型 |
| `frontend/src/pages/MlDetection/index.tsx:56-68` | `getModels()` 成功结果直接写入 `models` |
| `frontend/src/pages/MlDetection/index.tsx:71-89` | 并行读取 5 个辅助状态接口 |
| `frontend/src/pages/MlDetection/index.tsx:603-656` | `models.length`、`models.map` 和桌面模型表依赖数组 |

`/api/v1/ml/models` 需要 `MlModelInfo[]`，但收到分页对象。因为它仍是成功响应，`.catch(() => [])` 不会执行，最终 `models.map` 不是函数，表格无法出现。

需要覆盖的 GET 接口为：

1. `/api/v1/ml/health`
2. `/api/v1/ml/models`
3. `/api/v1/ml/buffer/stats`
4. `/api/v1/ml/drift/status`
5. `/api/v1/ml/shadow/stats`
6. `/api/v1/ml/train/status`
7. `/api/v1/ml/train/data-readiness`

### 3.4 静默跳过的位置

`frontend/e2e/table-layout.spec.ts:41-44`：

1. 只查找 `.tds-content .ant-table`。
2. 如果数量为 0 或第一张表不可见，直接执行 `test.skip`。
3. 没有区分“移动端按设计使用卡片”和“桌面表格因页面错误未渲染”。

因此 Pipeline、ML 的桌面错误与 Overview 390px 的正常移动卡片行为被归为同一种“无表格”情况。

## 4. 根本原因

### 4.1 通用空分页对象被错误当成所有 GET 接口的安全默认值

分页列表、对象、数组和聚合状态的响应契约不同。用 HTTP 200 返回一个泛型 `EMPTY_PAGE` 会绕过页面错误处理，并把错误推迟到渲染阶段。

### 4.2 Mock 没有和 TypeScript 响应类型建立约束

当前测试 fixture 是无类型对象，修改接口或新增页面时，编译器无法发现响应结构不匹配。

### 4.3 `test.skip` 根据运行结果动态决定，而不是根据设计声明

“没找到表格”本应是桌面用例失败条件，却被当成可接受条件。跳过策略没有显式登记允许跳过的路由、视口和替代组件。

### 4.4 用例没有监听页面错误和未知接口

即使页面发生 `pageerror` 或出现未覆盖 API，当前断言也只关注表格 DOM，错误原因不会直接体现在测试报告中。

## 5. 建议修复方案

### 5.1 建立类型化的 Pipeline/ML fixtures

在 E2E helper 中用项目类型或 `satisfies` 建立最小但完整的测试数据：

- `PIPELINE_HEALTH_FIXTURE satisfies PipelineHealthResponse`
- `ML_HEALTH_FIXTURE satisfies MlHealthStatus`
- `ML_MODELS_FIXTURE satisfies MlModelInfo[]`
- `ML_BUFFER_FIXTURE satisfies MlBufferStats`
- `ML_DRIFT_FIXTURE satisfies MlDriftStatus`
- `ML_SHADOW_FIXTURE satisfies MlShadowStats`
- `ML_TRAINING_FIXTURE satisfies MlTrainingStatus`
- `ML_READINESS_FIXTURE satisfies MlDataReadiness`

Fixture 至少包含一条可见表格数据，并使用较长服务名、模型路径，确保同时覆盖单行省略和 Tooltip 场景。

### 5.2 按路径精确分发，取消危险的万能成功响应

1. 将已知 API 路径映射到明确 fixture，不再让非分页接口落入 `EMPTY_PAGE`。
2. `EMPTY_PAGE` 只用于明确声明为分页响应的接口。
3. 未登记 GET 请求应记录到 `unexpectedRequests`，并返回明确的 501 测试错误或让当前测试失败，不能继续返回伪成功数据。
4. 如果不同路由需要不同响应，拆成按页面注册的 helper，避免一个全局 catch-all 不断膨胀。

### 5.3 用“预期展示模式”替代通用 `test.skip`

为路由和视口明确登记：

- `table`：必须出现指定数量的可见表格；未出现立即失败。
- `cards`：必须出现移动端记录卡片；不是跳过，而是断言替代视图。
- `empty-state`：只有业务设计明确为空态时才登记，且必须断言空态文案或组件。

当前页面建议：

| 页面 | 1440/1024 | 390 |
| --- | --- | --- |
| Pipeline | 必须显示服务状态表 | 必须显示 `.tds-operate-mobile-records` |
| ML | 必须显示模型状态表 | 必须显示 `.tds-operate-mobile-records` |
| Overview | 必须显示桌面表格 | 断言对应移动端卡片/替代内容 |

删除 `table-layout.spec.ts:42-44` 的通用运行时跳过。若确需跳过，必须是代码审查可见的静态登记，并写明业务原因。

### 5.4 增加错误监听和语义等待

1. 用例开始时监听 `page.on('pageerror')`，结束时断言数组为空。
2. 监听 `console.error`；只允许极少量明确登记的浏览器噪声，其他错误导致失败。
3. 断言 `unexpectedRequests` 为空。
4. 不依赖轮询页面的全局 `networkidle` 作为唯一就绪条件；改为等待目标表格、卡片或加载状态消失。
5. 对 Pipeline 10 秒自动刷新使用稳定 Mock，避免测试刚完成时触发未处理请求。

### 5.5 给 Mock 本身增加契约测试

1. TypeScript 编译必须能验证 fixture 满足接口类型。
2. 增加轻量单元测试，检查每个路径返回的顶层形状：对象、数组、分页对象不得混用。
3. 对未知路径做一次负向测试，确认不会再返回 `EMPTY_PAGE + 200`。

## 6. 潜在影响

- 修复后 E2E 可能暴露其他长期被通用 `EMPTY_PAGE` 掩盖的页面错误；这是测试可信度恢复后的预期结果，不应通过新增 skip 规避。
- 严格的未知请求策略会要求补齐更多 fixture，测试维护成本会上升，但能防止伪通过。
- Pipeline 有自动轮询，测试销毁和路由处理必须避免异步请求泄漏。
- 该任务原则上只修改 E2E 测试和 fixture，不应改变生产页面、真实接口或业务错误处理。
- Fixture 引入生产类型时应使用 `import type`，避免测试构建产生运行时依赖。

## 7. 验证方法与验收标准

### 7.1 定向测试

1. 运行 Pipeline 在 1440、1024、390px 的三组用例。
2. 运行 ML 在 1440、1024、390px 的三组用例。
3. 桌面/平板断言至少一张表可见且至少一行数据被渲染。
4. 移动端断言记录卡片可见，不使用 `test.skip`。
5. 故意删除一个 fixture 字段，确认 TypeScript 或测试能够失败。
6. 故意访问未登记 GET 路径，确认用例失败并输出路径。

### 7.2 全量测试

- 表格 E2E 不再出现 Pipeline/ML 桌面跳过。
- 预期的移动端替代视图通过正常断言计入“通过”，而不是计入“跳过”。
- `pageerror`、未知 API、非预期 `console.error` 均为 0。
- 继续执行 Lint、TypeScript、Vitest 和生产构建，确认测试 helper 没有破坏现有测试环境。

### 7.3 通过标准

- Pipeline/ML 所有 GET Mock 与 `frontend/src/types/index.ts` 类型一致。
- 1440/1024 下两页的表格真实执行布局断言。
- 390px 下断言移动卡片，不静默跳过。
- 缺表、页面异常或未知 API 会导致明确失败。

## 8. 本阶段结论

根因不是生产表格样式，而是 E2E 用 HTTP 200 返回了错误的数据形状，再由通用 `test.skip` 掩盖渲染失败。应先修复本问题，再开展 `INTERACTION-004` 的全量覆盖矩阵，否则扩大矩阵只会扩大伪通过范围。
