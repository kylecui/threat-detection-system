## 2. 问题描述

本问题包含相互关联但必须分别处理的两个层面。

### 2.1 Overview 浏览器用例在默认并发下不稳定

Windows 复查中，`frontend/e2e/overview-trend.spec.ts` 在项目默认 4 workers 组合回归下 3/3 超时；相同源码以单 worker 运行时 3/3 通过。失败截图已经显示趋势图或空态最终正确出现，说明生产 DTO 映射并未失败，超时发生在默认 5 秒断言窗口和页面实际完成渲染之间。

### 2.2 Ubuntu 构建机无法准备 Chromium

在正式构建机 `192.168.100.9` 上：

1. 项目没有已安装的系统 Chrome/Chromium；
2. Playwright 浏览器缓存为空；
3. Debian 官方源连接超时，需要临时切换可达镜像才能安装系统依赖；
4. Playwright 官方 Chromium CDN 长时间保持 0%；
5. `npmmirror` 对当前 Chromium revision 1217 的 CFT 文件返回 404。

因此 Ubuntu 复查没有执行到 Overview 用例本身。该结果属于测试运行环境未准备成功，不是用例失败，也不能作为通过证据。

## 4. 根本原因

### 4.1 用例只观察请求出现，没有等待响应和状态提交

第一条用例在 `frontend/e2e/overview-trend.spec.ts:33-37` 监听 request 并记录 `hours`，随后：

- 初次加载只执行 `page.goto()`；
- 范围切换只点击按钮；
- `expect.poll(() => hours.includes(expected))` 只证明请求已经发出；
- 没有证明响应成功、`loadData` 完成、React 状态提交和图表挂载完成。

第二、三条用例同样在 `page.goto()` 后立刻进入可见性断言。

### 4.2 默认 5 秒断言窗口与并发资源竞争形成临界条件

`playwright.config.ts` 没有配置全局 `expect.timeout`，因此可见性断言使用 Playwright 默认等待时间。4 workers 并发时，以下工作会竞争 CPU、内存和 Vite 转换资源：

- 多页面同时加载大型 React/Ant Design 模块；
- Mock 路由和认证初始化；
- Overview 快照请求及状态更新；
- Ant Design Charts 的 Canvas 初始化。

失败截图在断言超时后已经显示正确界面，单 worker 又稳定通过，符合“正确结果晚于断言边界出现”的时序特征，而不是 DTO 内容错误。

### 4.3 CI 配置会掩盖本地默认并发问题

`frontend/playwright.config.ts:8` 在 CI 环境把 workers 固定为 1。这样 CI 可能通过，而开发者按默认配置运行 4 workers 时失败，导致相同测试在不同入口下给出不一致结论。

不建议简单把所有环境都改成单 worker；这会回避并发稳定性要求，并显著增加完整回归耗时。

### 4.4 正式构建流程没有独立、版本锁定的 E2E 浏览器运行时

当前项目只锁定 NPM 包版本，没有为 `192.168.100.9` 提供以下任一能力：

- 与 Playwright 1.59.1 匹配的预装浏览器镜像；
- 经校验的离线 Chromium revision 1217；
- 可复用的系统 Chrome 路径；
- Ubuntu E2E 启动脚本和环境预检。

因此每次都依赖 `npx playwright install` 在线下载，构建机网络一旦无法访问 CDN，浏览器验收就无法开始。

## 6. 详细修复方案

修复分为“用例同步”和“Ubuntu 运行环境”两条并行工作线，两者都完成后才能验收。

### 6.1 工作线 A：用响应完成事件同步 Overview 用例

在 `frontend/e2e/overview-trend.spec.ts` 增加测试内辅助函数，按 URL 路径、`hours` 参数和成功状态等待快照响应。例如：

```ts
function waitForSnapshot(page: Page, hours: string) {
  return page.waitForResponse((response) => {
    const url = new URL(response.url());
    return url.pathname.endsWith("/api/v1/assessment/overview-snapshot")
      && url.searchParams.get("hours") === hours
      && response.ok();
  }, { timeout: 15_000 });
}
```

具体调整：

1. 初次进入页面前先创建 `waitForSnapshot(page, "24")` Promise，再执行 `page.goto()`，随后等待响应 Promise。
2. 对 7 天和 30 天切换，使用 `Promise.all([waitForSnapshot(...), button.click()])`，确保监听先于点击生效。
3. 删除只收集 request 的 `hours` 数组和 `expect.poll(() => hours.includes(...))`；请求出现不等于数据已经渲染。
4. 响应成功后，再在趋势面板作用域内等待图表或空态。
5. 图表/空态可使用明确的局部 10–15 秒超时；不要放大全局 `expect.timeout`，避免掩盖其他测试性能回归。
6. 范围切换后同时断言目标 Segmented 项已选中、对应响应已完成、图表 Canvas 仍存在。
7. 保留 `pageerror` 和 `unexpectedRequests` 断言。

快照服务对 `24/168/720` 使用不同缓存 key；当前用例每个 key 只首次请求一次，因此精确等待响应不会与现有缓存冲突。未来如果测试重复访问已缓存的同一范围，必须先判断是否预期发起网络请求，不能机械等待不存在的响应。

### 6.2 不通过降低并发或增加重试掩盖问题

不得仅采用以下方式：

- 把整个项目改为 `workers: 1`；
- 给该 describe 设置 serial 后直接宣称并发问题解决；
- 增加 retries 让偶发失败被重试吞掉；
- 只把默认超时提高到很大数值而不等待快照响应；
- 恢复生产代码中的 `count/value` 双字段兼容回退。

### 6.3 工作线 B：建立版本锁定的离线 Playwright 运行环境

推荐为构建机准备官方版本匹配的测试镜像，不把浏览器加入生产安装包。

在可联网的 Ubuntu x86_64 机器上：

```bash
docker pull mcr.microsoft.com/playwright:v1.59.1-noble
docker save mcr.microsoft.com/playwright:v1.59.1-noble \
  | gzip -1 > playwright-v1.59.1-noble.tar.gz
sha256sum playwright-v1.59.1-noble.tar.gz \
  > playwright-v1.59.1-noble.tar.gz.sha256
```

将镜像归档和校验文件传到构建基础设施专用缓存目录，不得放入 `outputs/v<version>/` 或威胁检测系统生产 tar.gz。建议远端位置：

```text
/home/jzzn/e2e-images/
```

在 `192.168.100.9`：

```bash
cd /home/jzzn/e2e-images
sha256sum -c playwright-v1.59.1-noble.tar.gz.sha256
gzip -dc playwright-v1.59.1-noble.tar.gz | docker load
docker image inspect mcr.microsoft.com/playwright:v1.59.1-noble
```

在导入前先运行 `df -h` 和 `docker system df`。当前构建盘余量曾只有约 1.8 GiB，应为浏览器镜像、项目 `node_modules`、测试报告和临时层预留至少 4 GiB。若空间不足，只能在确认归属后清理本任务产生的临时资源；不得自动 prune 或删除其他项目镜像、卷和构建目录。

### 6.4 增加可重复的 Ubuntu E2E 启动脚本

实施阶段建议新增测试专用脚本，例如：

```text
scripts/testing/run_frontend_e2e_ubuntu.sh
```

脚本应：

1. 校验主机为 x86_64 Linux；
2. 校验指定 Playwright 镜像已经存在；
3. 从 `package-lock.json` 检查 Playwright 版本与镜像标签一致；
4. 检查磁盘和共享内存；
5. 使用 `--shm-size=1g` 启动容器；
6. 挂载 `frontend` 源码；
7. 使用可达的 NPM registry 执行锁文件安装；
8. 按传入参数运行 Playwright，并把报告写回项目测试目录；
9. 保留真实退出码，不允许失败后返回 0。

`scripts/pack_release.py` 采用显式生产文件清单，新测试脚本不会自动进入正式包；仍应通过发布契约确认这一边界。

系统 Chrome + `PLAYWRIGHT_EXECUTABLE_PATH` 可以作为临时诊断后备，但正式 Ubuntu 验收优先使用与 Playwright 1.59.1 匹配的固定镜像，避免系统 Chrome 自动升级后产生新的版本漂移。

### 6.5 版本和发布策略

007/010 修复会改变仓库测试源码和质量证据。完成后应升级到新版本（建议 `3.1.38`），不要继续覆盖已经存在多个不同哈希的 3.1.37 归档。

新版本只有在 lint、Ubuntu 4-worker E2E 和正式发布契约都通过后才能打包回传。

## 7. 潜在影响与风险

### 7.1 用例代码风险

- URL 匹配过宽可能把客户/租户其他趋势请求误认为快照；应同时匹配 pathname 和 `hours`。
- 在点击之后才注册 `waitForResponse` 会漏掉快速 Mock 响应；必须先建立 Promise。
- 全局提高 timeout 会延长所有真实失败的反馈时间；只使用局部超时。
- 仅断言 wrapper 可见可能无法证明 Canvas 已挂载；普通和全 0 场景应保留 Canvas 数量断言。
- 空态用例必须继续断言图表不存在，避免空态和图表同时出现。

### 7.2 运行环境风险

- Playwright NPM 包与镜像标签不一致会出现浏览器 revision 不匹配；两者必须同时锁定为 1.59.1。
- 官方镜像体积较大，当前构建机磁盘容量紧张；导入前必须预检。
- 以 root 容器直接写宿主 `node_modules` 可能留下 root 所有者文件；实现脚本应使用命名卷，或明确映射构建用户 UID/GID 和可写缓存目录。
- 不得把测试镜像或浏览器二进制塞进生产发布包，否则会显著放大交付物并破坏现有发布契约。

### 7.3 生产功能影响

计划只修改 E2E 同步和测试基础设施，不修改 Overview API、DTO、映射函数或页面业务逻辑。若实施中发现必须调整生产页面，应停止并另建问题，不得把业务修改混入本问题。
