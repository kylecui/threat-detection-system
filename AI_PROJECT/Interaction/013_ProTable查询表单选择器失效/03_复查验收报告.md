## 2. 文档结论复核

第二阶段对第一阶段根因作了必要校正：依赖版本中 `.ant-pro-table-search` 并非必然不存在，Ubuntu 原失败截图也显示 Query 尚在 loading；直接失败更可能与 011 冷启动竞争有关。最终修复没有继续依赖对第三方内部 DOM 的推断，而是建立应用自有查询区契约，这一方向正确且更稳健。

## 3. 代码复核

1. `frontend/src/components/proTableConfig.ts:10-13` 定义应用自有 `tds-table-query` class 和统一 `PRO_TABLE_SEARCH`。
2. 4 个 ProTable 均使用 `search={PRO_TABLE_SEARCH}`：
   - 客户列表：`frontend/src/pages/CustomersAndDevices/index.tsx:1100`
   - 设备列表：`frontend/src/pages/CustomersAndDevices/index.tsx:1737`
   - 告警列表：`frontend/src/pages/AlertCenter/index.tsx:754`
   - 威胁指标：`frontend/src/pages/ThreatIntel/index.tsx:701`
3. `frontend/src/index.css:1246-1263` 的查询区布局与标签样式只依赖应用自有 class。
4. `frontend/e2e/helpers/queryFilter.ts` 通过可见的 `.tds-table-query` 和字段可访问名称定位，不再把第三方内部 class 当成稳定接口。
5. `frontend/e2e/query-filter.spec.ts` 覆盖 4 个查询区 × 2 个视口 × 2 种语言；导航对齐用例也先等待页面和表格就绪。
6. 源码与 E2E 执行代码中未发现继续使用旧 `.ant-pro-table-search` 定位业务查询区的实现。

## 5. 风险与后续要求

1. 该契约依赖所有新增 ProTable 都复用 `PRO_TABLE_SEARCH`。应保留静态合同，新增表格若直接传入独立 search 配置，必须显式包含应用 class。
2. 可访问名称属于用户文案的一部分；翻译调整后 E2E 正则需要同步，但不应回退到第三方结构选择器。
3. 011 自身尚未通过不会推翻本问题的定向结论；不过发布总门禁仍需等待 011、014 的全量回归恢复绿色。
