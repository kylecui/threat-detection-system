## 2. 根因复核（与第一阶段结论有出入，请复查时注意）

我对照了你本机安装的依赖与真实 DOM，结论如下：

1. **`ant-pro-table-search` 类名在当前版本中仍然存在。** 本机 `@ant-design/pro-table` 为 3.21.0，`es/components/Form/FormRender.js` 第 148 行 `getPrefixCls('pro-table-search')` 会给查询表单外层包裹 `div` 加上该类。这个文件与工作区副本逐字节一致，`pro-components` 下也没有嵌套的其他版本。本地真实渲染的 DOM 链为：
   - `.ant-pro-table-search.ant-pro-table-search-query-filter.ant-pro-card`（外层，带 1px 边框）
   - `> .ant-pro-query-filter-container`
   - `> form.ant-pro-query-filter`（内层，灰底，padding 14px，来自页面级 CSS）

   Ubuntu 失败截图中的查询区也是同样的“白色带边框卡片 + 内部灰色查询框”结构。
2. Ubuntu 失败时的页面快照里，“Query”按钮仍处于 **loading** 状态。因此该次失败**最可能的直接原因是 011 所述的冷启动就绪竞争**：5 秒断言窗口内查询表单尚未挂载，失败截图是在超时之后才采集的。它不是确定性的类名失效。
3. 第一阶段指出的风险仍然成立：测试和全局 CSS 把 Pro Components 的**内部类名**当作唯一入口，而这些类名不是公开 API。另外，全局查询区规则的背景色被 Pro Card 的 CSS-in-JS 覆盖，只有部分声明生效。

所以本问题仍按方案修复，目标调整为**不再依赖第三方内部类名，并同步页面就绪**，而不是“把旧类名换成另一个内部类名”。

## 3. 修复结果总结

1. **应用自有 hook**（步骤二、四）：新增 `src/components/proTableConfig.ts`，导出 `PRO_TABLE_SEARCH = { labelWidth: "auto", className: "tds-table-query" }`。4 个 ProTable（客户、设备、告警明细、威胁情报指标）统一改为 `search={PRO_TABLE_SEARCH}`。ProTable 会把 `search.className` 加到查询表单外层（即上面那个包裹 `div`），项目自己的类名因此与原内部类名位于同一个元素上。
2. **全局样式入口**（步骤一）：`index.css` 中两条规则（查询区外框，以及标签按 38px 控件高度垂直居中）改用应用自有 hook：
   - 外框规则：`.tds-content .ant-pro-table-search` 改为 `.tds-content .tds-table-query:where(div)`；
   - 标签规则：改为 `.tds-content .tds-table-query .ant-form-item-label > label`。

   验证中发现，ProTable 不仅把 `search.className` 加到外层 `div`，也会传给内层 QueryFilter 的 `<form>`。如果直接写 `.tds-content .tds-table-query`，外框规则会同时作用到内层表单，使它多出 1px 边框和 16px 下边距，表单高度由 66px 变为 68px。`:where(div)` 只匹配外层包裹元素，而且 `:where` 不增加特异性，选择器仍为原来的 (0,2,0)，位置也不变，所以**层叠结果与修复前完全一致**。
3. **页面级规则审核**（步骤一第 3 点）：`governance.css` 和 `investigate.css` 对内层 `.ant-pro-query-filter` 设置的背景、内边距、间距，属于各页面在卡片内的布局，包括 640px 以下的窄屏内边距。如果合并到全局规则，特异性更高的全局规则会覆盖窄屏规则，造成回退，因此保留，不做合并。
4. **E2E 定位**（步骤二）：
   - 新增 `e2e/helpers/queryFilter.ts`：`tableQuery()` 通过 `.tds-content .tds-table-query:visible` 定位当前可见的查询区（非激活 Tab 中的 ProTable 仍然挂载，需要排除）；
   - `tableQueryField(page, name)` 按**可访问名称**（例如 “Customer ID”）定位输入框，再找到所属表单项的标签和控件；
   - helper 中不出现任何 `.ant-pro-*` 类名。
5. **导航用例**：先 `gotoReady` 加 `waitForTableReady`，再通过 `tableQueryField(page, /Customer ID/)` 测量标签与控件的中心差（≤ 2px）。
6. **覆盖矩阵**（步骤三）：新增 `e2e/query-filter.spec.ts`，覆盖客户、设备、告警明细、威胁情报指标 4 个页面 × 1440/390 × 中/英，共 16 个用例。折叠和展开（存在“展开”按钮时）两种状态分别检查：
   - 每个标签和控件都在查询区内；
   - 标签与控件不重叠；
   - 1440 下标签与控件垂直居中（≤ 2px）；
   - 重置、查询、展开按钮都在查询区内；
   - 页面不出现横向滚动。

   最后再收起，确认“展开”按钮恢复。
7. **防止复发**（步骤四第 3 点）：契约测试禁止在 `src`、`e2e` 中出现 `ant-pro-table-search`，并要求 4 个 ProTable 都使用共享配置。

## 5. 测试结果

| # | 验证 | 结果 |
| --- | --- | --- |
| 1 | `query-filter.spec.ts` 与导航中的标签对齐用例，`--workers=4` | **17/17 通过** |
| 2 | 展开状态是否真的被检查 | 8 个“页面 × 宽度”组合中有 6 个存在“展开”按钮并执行了展开检查（设备、告警明细在 1440 下字段已全部显示，没有展开按钮） |
| 3 | 静态契约（本问题 4 项） | **通过**；在修复前代码上 4 项全部失败 |
| 4 | 搜索 `ant-pro-table-search` | `src`、`e2e` 中**零命中** |
| 5 | 视觉（计算样式与几何逐项比对） | 修复前后，在 4 个页面 × 1440/390 共 8 个组合中，比对外层包裹、内层表单、标签的 margin、padding、边框、圆角、背景、标签对齐属性，以及外层和表单的边界框：**完全一致**。第一版选择器在这一步测出内层表单高了 2px，已改为 `:where(div)` 修正 |
| 6 | 汇总回归 | 见 011 文档第 7 节；4 个页面的查询、重置、展开、分页、排序都在全量用例中执行 |

**本地环境说明**：本地浏览器版构建中，ProTable 使用 pro-components 自带的 antd 5.25.4，不会读取应用主题中 38px 的控件高度，所以标签与控件相差约 3px。这正是此前该用例在本地失败 1px 的原因，与本问题无关。因此仅在 `E2E_LOCAL_UMD_BUILD=1` 时跳过“1440 居中”这一项断言，并在报告中加注释；其余检查照常执行。在 Vite 开发环境和 Ubuntu 镜像中**不设置**该变量，居中断言照常执行。

## 6. 未解决问题与注意事项

1. 需要在 Vite 环境（本机 `npm run dev` 或 Ubuntu 镜像）中复跑 `e2e/query-filter.spec.ts` 和导航的标签对齐用例，确认 1440 下居中误差 ≤ 2px：

   ```bash
   scripts/testing/run_frontend_e2e_ubuntu.sh e2e/query-filter.spec.ts e2e/navigation.spec.ts --workers=4
   ```

2. 以后新增 ProTable 时必须使用 `search={PRO_TABLE_SEARCH}`；需要额外字段时用展开语法 `{ ...PRO_TABLE_SEARCH, ... }`，保留 `className`。
3. 依赖升级检查清单建议加入一条：“ProTable 查询区 `search.className` 仍然加在查询表单外层”。`query-filter.spec.ts` 会在 hook 失效时直接失败。
