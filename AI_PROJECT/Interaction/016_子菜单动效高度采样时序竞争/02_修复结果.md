## 2. 根因确认

1. **复现**：在修复前代码上，把浏览器 CPU 降速（Chrome DevTools 的 `Emulation.setCPUThrottlingRate`）以模拟 4-worker 全量运行时的负载，单独重复运行 measured-height 用例：

   | 降速 | 失败 | 其中 `NaN`（收起阶段） | 其中 `NaN`（展开阶段） | 其中 class 断言错过动画窗口 | 其中 600ms 期限 |
   | --- | --- | --- | --- | --- | --- |
   | 4 倍 | **15/20** | 9 | 3 | 3 | 0 |
   | 6 倍 | **17/20** | 8 | 6 | 2 | 1 |

   收起阶段的 `NaN` 与 Ubuntu 失败完全相同。复现还暴露了第一阶段没有提到的两类同源问题：
   - **展开阶段也有同样的竞争**：先等到 `enter-active`，再另起一次读取 `node.style.height` 时，动画已经结束、内联高度已被清除，`parseFloat('')` 同样得到 `NaN`；
   - 自动重试的 `toHaveClass(/leave-active/)` 断言本身也会**完全错过**只有约 210ms 的动画窗口。
2. **原因**与第一阶段分析一致：
   - “class 处于 active”和“读取高度”分属两次浏览器往返，属于检查时与使用时不一致（TOCTOU）；
   - 读取的是可能为 `auto` 的 CSS `height`，又没有做有限数检查。
3. **产品动画无缺陷**：修复后的帧记录显示，收起和展开过程中每一帧都有有限的几何高度，过渡时长正确，没有残余样式（见 4.2）。因此没有修改产品代码（方案 5.5）。

## 3. 修复内容

### 3.1 动效帧记录器 `recordSubmenuMotionFrames`（方案 5.1）

位于 `navigation.spec.ts` 第 29–108 行，在点击**之前**安装：

- **采样时机**：
  - `MutationObserver` 监听 `class` 和 `style` 属性，每次变化都采一帧；
  - `requestAnimationFrame` 循环：只要带有 `tds-submenu-motion-enter/leave` class，每个渲染帧都采一帧。
- **每帧是一个同步快照**：在同一个 JS 任务中读取 `time`、`source`、`className`、内联 `height`、computed `height`、`getBoundingClientRect().height`、`scrollHeight`、`maxHeight`、`opacity`、`transform` 和 `transitionDuration`。所以“class 处于 active”和“高度”必然属于同一帧。
- **数量上限**：600 帧（`MOTION_FRAME_LIMIT`）。达到上限后不再采样，也停止调度 rAF，防止样本无限增长。
- **显式清理**：`stop()` 会断开 observer、取消 rAF，并删除节点上的测试专用属性 `__tdsMotionRecorder`。
  - 每个阶段都在 `finally` 中调用，失败时也会执行；
  - `stop()` 自身有 1 秒上限，节点已被移除时也不会抛错；
  - 对同一节点重复安装时，会先停止旧的记录器。
- **类型完整**：使用 `MotionFrame`、`MotionRecorderHost` 接口，没有 `any`。

原来的 `recordClassHistory` 从不断开 observer。它已被删除，四个工作区场景改用新的记录器（只读取帧中的 `className`），断言内容不变。这样同一文件只有一个带清理机制的记录器。

### 3.2 measured-height 用例（方案 5.2、5.3）

位于第 603–678 行，两次点击前各安装一次记录器：

- **收起**：
  1. 用 `expect.poll` 确认记录中出现过 `leave-active`；
  2. 断言 `aria-expanded=false`；
  3. 菜单在 600ms 内变为 `ant-menu-hidden`（原有断言，期限不变）；
  4. 对完整帧记录做如下断言：
     - 每个 `leave-active` 帧的几何高度都是有限数；
     - 至少存在一个 `leave-active` 帧**同时满足** `validLeaveFrame`：0 ≤ 高度 ≤ 自然高度（容差 0.5px）、`transition-duration` 包含 `0.21s`、`max-height: none`、opacity 可解析且在 0–1 之间、transform 的纵向位移在 0 到 −5.5px 之间（向上收起）；
     - `leave-active` 帧的高度单调不增。该检查允许动画从快速反转后的中间高度开始。
- **展开**：
  1. 确认出现过 `enter-active`；
  2. 断言 `aria-expanded=true`；
  3. `enter-active` 在 700ms 内被清理（原有断言，期限不变）；
  4. 至少存在一个 `enter-active` 帧同时满足 `validEnterFrame`：
     - 内联目标高度是有限像素值，并且**同时等于**该帧的 `scrollHeight` 和收起前测得的自然高度；
     - 几何高度不超过自然高度；
     - `transition-duration` 包含 `0.26s`。
- **原有结束断言全部保留**：“Alert Center”链接可见、箭头图标处于展开状态、内联 `style` 中不再含 `height`。
- **失败诊断**：断言消息附带自然高度和完整帧序列，每帧包含相对时间、采样来源、精简后的 class、内联/computed/矩形高度、scrollHeight、max-height、opacity、transform 和过渡时长。这样能直接区分以下情况：未进入 active、进入后没有像素高度、过渡配置丢失、采样发生在清理之后。
- **没有使用的做法**：不再先等待 class、再另起一次读取样式；不再对 CSS `height` 执行 `parseFloat`；没有把 `NaN` 当作 0；没有使用 `waitForTimeout`。

### 3.3 关于“目标高度”的加强（自查时发现）

我故意把产品代码的展开目标改成 `scrollHeight + 24` 来检验断言。按照第一阶段写法（只与当帧的 `scrollHeight` 比较），用例**仍然通过**：盒子高于内容时，`scrollHeight` 会随盒子一起变大，最后一帧两者恰好相等。

因此 `validEnterFrame` 增加了“等于收起前测得的自然高度”这一条件。修改后，上述故意破坏能被识别。原用例也有同样的漏洞。

### 3.4 静态合同（方案 5.4）

`tests/test_e2e_stability_contracts.py` 的 `WorkspaceMotionContract` 新增 2 项：

- **`test_motion_recorder_samples_atomically_and_cleans_up`**：
  - 记录器同时监听 `class` 和 `style`，并使用 rAF；
  - 每帧读取 className、矩形高度、computed/内联高度、scrollHeight、过渡时长；
  - 包含 `disconnect`、`cancelAnimationFrame`、删除临时属性和数量上限；
  - 旧的 `recordClassHistory` 不得再出现；
  - 文件中不得出现 `any`。
- **`test_measured_height_test_uses_same_frame_samples`**：
  - 用例内不得出现 `parseFloat(style.height)`，也不得出现“`toHaveClass(active)` 之后紧跟一次 `evaluate` 读取样式”的写法；
  - 恰好安装 2 次记录器，每次都在点击之前，并在 `finally` 中 `stop()`；
  - 必须调用 `validLeaveFrame`、`validEnterFrame`、`Number.isFinite` 和 `describeFrames`；
  - 必须保留 600ms、700ms、`aria-expanded` 和内联 height 清理等原有断言；
  - 两个判定函数必须包含有限数、范围、`0.21s`/`0.26s`、`max-height`、方向和自然高度等条件。

原有的“四个独立用例”和“相关动效用例仍存在”合同保持不变。另外，同一文件中侧栏用例对固定高度侧栏执行 `parseFloat(style.height)` 是合理的，合同只在 measured-height 用例范围内禁止该写法。
