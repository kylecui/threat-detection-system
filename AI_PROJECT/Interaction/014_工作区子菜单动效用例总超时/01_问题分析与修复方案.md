# INTERACTION-014：工作区子菜单动效用例总超时

## 1. 文档状态

- 阶段：问题分析与修复方案。
- 结论：已定位为一个测试中串行执行四组独立场景、累计超过 Playwright 默认 30 秒；**本阶段未修改源码**。
- 影响：完整 Ubuntu 回归中 `all workspace submenu parents share the same motion behavior` 失败。

## 2. 问题描述

该测试依次切换四个工作区：

1. Threat operations / Investigate；
2. Platform health / Operate；
3. Organization / Admin；
4. Configuration / Configuration。

每个工作区都执行一次展开状态检查、收起动画、隐藏状态、再次展开动画和结束状态检查。完整运行约 31 秒，在第四组场景中触发 Playwright 默认 30 秒 test timeout。失败截图仍停留在 Organization，说明测试预算在进入或等待第四组 Configuration 时耗尽。

现有报告没有证据表明某个工作区的产品动画参数错误。测试将四个独立产品场景捆绑在一个总计时器中，导致失败既不稳定，也无法精确指出是哪一组行为回退。

## 3. 根本原因

### 3.1 单个测试承载四个独立场景

`navigation.spec.ts` 在一个 `for` 循环中串行切换四个工作区。每次包含弹出菜单、路由/工作区状态更新、submenu DOM 更新以及收起/展开动画，总时间随场景线性增长。

### 3.2 动效本身具有真实持续时间

应用为二级菜单配置 `motionDeadline: 360ms`，CSS 收起约 210ms、展开约 260ms，测试又分别允许 600ms 和 700ms 等待动画结束。这些都是为验证真实空间连续性而存在，不应通过关闭动画来缩短测试。

### 3.3 Playwright 未设置该用例的专用超时

`playwright.config.ts` 未配置 `timeout`，采用默认 30 秒。用例总耗时约 31 秒，因此即使每个单场景都正确，第四组仍可能被总超时截断。

### 3.4 缺少工作区切换完成的显式同步

点击工作区菜单项后，测试立即按父菜单文本定位。它没有先确认切换按钮名称、工作区 header/accent 和对应父菜单均已稳定，冷模块/状态更新会进一步消耗默认 locator 等待时间。

## 5. 详细修复步骤

### 步骤一：将四个场景参数化为四个独立测试

1. 提取 `assertWorkspaceSubmenuMotion(page, scenario)` 公共断言函数。
2. 使用场景数组生成四个独立 `test()`，每个测试只切换并验证一个工作区。
3. 每个测试从明确的 `/overview`、固定认证、固定语言和展开状态开始，避免前一场景状态污染下一场景。
4. 测试标题包含 workspace 与 parent，失败时可直接定位具体工作区。

### 步骤二：增加工作区切换完成条件

1. 点击工作区后等待 Switch workspace 按钮显示目标工作区名称。
2. 等待目标 workspace 的父菜单唯一可见，并确认 `aria-expanded=true`。
3. 如工作区切换会改变 route/accent/header，同步验证对应稳定状态后再开始动画断言。

### 步骤三：保留并精确验证真实动画

1. 收起时验证 leave start/active、动态高度、opacity/translate、`aria-expanded=false` 和最终 `ant-menu-hidden`。
2. 展开时验证 enter active、目标高度等于 `scrollHeight`、`aria-expanded=true` 和动画 class 清理。
3. 继续运行已有“快速反转无残影”和 `prefers-reduced-motion` 用例，避免拆分后只覆盖正常点击。
4. 避免用大段固定 `waitForTimeout()`；等待可观察的 class、attribute 和 animation finished 状态。

### 步骤四：谨慎处理超时

拆分后每个测试应优先在默认 30 秒内完成。只有单个真实动效场景经干净环境验证仍有合理需求时，才为该 describe/用例设置局部 45–60 秒上限。不得提高全局 timeout 来掩盖所有慢用例。

## 6. 潜在影响

1. 用例数量增加，beforeEach 运行次数增加，总套件时间可能略有上升，但并行执行后通常不会比当前串行测试更慢。
2. 若场景没有隔离本地存储中的 workspace，参数化后仍可能互相污染；每项必须显式初始化。
3. 仅放大 timeout 会保留失败定位模糊和状态耦合，明确不推荐。
4. 测试拆分不能降低产品动画检查强度，仍需检查高度、透明度、位移、箭头和展开状态同步。

## 7. 验证方法

1. 单独运行四个参数化用例，各自重复 5 次，确认没有超时或状态污染。
2. `navigation.spec.ts --workers=4 --repeat-each=3`，验证四个工作区均独立通过。
3. 完整 E2E `--workers=4`，确认不再出现 30 秒总超时。
4. 对动画中途快速反复点击，确认最终只有一个正确展开状态，无残影和错位。
5. 启用 `prefers-reduced-motion: reduce`，确认空间动画被压缩/取消但状态仍正确。

## 8. 验收标准

- 四个工作区分别有独立、可定位的测试结果。
- 每个场景在默认或明确的局部超时内稳定通过，不依赖提高全局 timeout。
- 展开/收起的高度、透明度、位移、箭头和 aria 状态保持同步。
- 快速反转、连续切换和 reduced-motion 行为不回退。
