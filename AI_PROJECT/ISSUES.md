## 已知限制 / 待后续处理

1. **EMQX 生产安全加固**：当前沿用匿名明文 `1883` 兼容接入，`8883` 仍是预留端口。非隔离网络部署前需要认证、ACL 和 TLS/mTLS 设计。
2. **数据库升级机制**：`docker-entrypoint-initdb.d` 只负责空数据卷；安装器会在升级时按顺序补执行现有 SQL，但尚未引入 Flyway/Liquibase 的版本表、校验和与失败恢复模型，后续复杂迁移仍需专项治理。
3. **目标机在线构建**：发布包携带源码并在目标机拉取基础镜像和依赖；离线部署需要后续增加预构建镜像包或镜像仓库流程。
4. **资源占用**：18 个常驻容器对单机 CPU、内存和磁盘压力较大，低规格环境不保证完整启动。
5. **告警服务旧测试债务**：`NotificationServiceTest` 的保存次数/mock 预期与现实现不一致，`KafkaConsumerServiceTest` 仍修改不可变测试对象；它们与 3.1.17 SMTP 改动无关，但全量告警服务测试仍会失败。3.1.17 使用独立的 `NotificationConfigControllerTest` 验证新增契约，旧测试需后续按现业务语义专项整理。
5. **默认端口暴露**：当前 Compose 延续将数据库、中间件和管理端口绑定宿主机的开发兼容设计，生产防火墙与最小暴露需要单独收敛。
6. **单机非 HA**：Compose 的 PostgreSQL、Kafka、Redis、EMQX 和宿主机均为单点；Kubernetes production overlay 的无状态副本不能替代有状态集群和跨故障域基础设施。
7. **长期保留**：42 号 SQL 提供大表索引和 autovacuum 基础，但尚未自动分区/删除/归档。每天数百万条且长期保留前必须确定保留周期和冷存储方案。
