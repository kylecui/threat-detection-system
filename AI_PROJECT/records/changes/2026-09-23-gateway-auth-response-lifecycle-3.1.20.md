# 3.1.20 网关认证响应生命周期整改

## 现场现象

- `/admin/customers` 文档可正常返回，但随后客户列表 XHR 显示网络错误，并发生一次有限重试。
- Customer Management 直连接口返回正常的空分页结果，容器健康且无重启，因此不是客户服务或数据库不可用。
- API Gateway 日志显示正常 `200 OK` 之后，`JwtAuthenticationFilter.unauthorized()` 又尝试修改只读响应头，抛出 `UnsupportedOperationException`。

## 根因

JWT 过滤器把账户查询后的 `switchIfEmpty` 放在了包含 `chain.filter(exchange)` 的响应链末尾。Gateway 下游链的返回类型是 `Mono<Void>`，成功完成时本来就不会发出数据元素，因此被错误解释为“账户不存在”，在已经提交的成功响应后再次写入 `401`。全局异常处理器随后又尝试改写同一响应，最终中断浏览器连接。

## 修改

- 先将账户查询转换为显式 `Optional` 分支，再进入下游 `Mono<Void>` 过滤链，彻底分离“实体不存在”和“请求成功完成”。
- 保留账户、租户、客户实时生命周期校验；缺失或失效账户在下游调用前返回 `401`。
- GlobalExceptionHandler 遇到已提交响应时只传播原始异常，不再二次修改状态码、响应头或响应体。
- 认证、RBAC 授权和限流的直接响应统一增加 `isCommitted()` 防御。
- 修正异常消息脱敏后的截断长度与 JSON 转义边界。
- 扫描各服务全部 `switchIfEmpty` 用法；其余位置均作用于实体查询，没有发现同类 `Mono<Void>` 误判。

## 兼容性边界

- 不改变 JWT 格式、账户/租户/客户状态规则、RBAC 权限或客户接口契约。
- 不改变 Customer Management、数据接入、数据库、消息队列及前端业务逻辑。
- 公共登录、首次管理员创建和健康检查仍按原白名单规则工作。

## 验证范围

- 成功认证：保留下游 `200`、响应头和 JSON 响应体，不追加 `401`。
- 缺失及停用账户：返回 `401` 且不进入下游。
- 已提交响应：全局异常处理器不改写已有内容。
- 认证、授权、限流及全局异常直接写响应路径均具备提交状态保护。
