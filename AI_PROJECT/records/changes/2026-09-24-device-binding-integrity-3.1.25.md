# 3.1.25 设备绑定一致性与写操作防重

## 发现的问题

- 设备绑定请求较慢时，第一次点击没有即时反馈，操作员再次点击会发出第二个 POST。
- 同一序列号可能生成两条当前绑定，页面出现两行相同设备和两次成功提示，后续解绑会因查询到多条记录失败。
- 批量绑定接口即使返回单项失败，页面仍可能仅按 HTTP 201 显示成功。
- 写操作普遍只依赖 React 状态禁用按钮，状态更新前存在同一渲染帧内的重复提交窗口。

## 根因

- 前端没有同步锁，请求发出到 React 重渲染之间仍可再次触发事件。
- 后端使用“查询不存在后再插入”，并发请求之间没有同一设备级事务锁。
- 16 号时效迁移为支持历史记录移除了 `dev_serial` 全局唯一约束，但没有增加“仅约束当前记录”的替代索引。
- Customer Management 和 Threat Assessment 均可写同一关系表，但写入语义与锁边界没有统一。
- `@Async` 方法在同一个 Service 内部自调用，实际不会经过 Spring 异步代理。

## 修改

- 新增通用 `useSubmitGuard`，以同步 ref 锁阻止同一渲染帧的连续提交，并在请求期间锁定弹窗操作。
- 绑定、解绑和转移按规范化序列号取得 PostgreSQL advisory transaction lock；客户批量绑定同时取得客户级锁，串行化配额判断。
- 新增 `45-device-binding-integrity.sql`：自动关闭旧重复当前绑定，创建大小写无关的部分唯一索引。
- 解绑改为设置 `is_active=false` 与 `unbind_time`，默认查询、计数和配额只读取当前绑定。
- 前端解析批量结果，失败时显示服务端单项原因；绑定相关请求关闭全局重复错误提示。
- 客户、设备、租户、用户、告警、AI、插件和配置级联等关键写操作补齐同步提交锁。
- 客户归属回填拆为独立 `DeviceBackfillService` 异步执行。

## 兼容与升级

- 历史绑定不会删除；迁移保留每个序列号最新的当前绑定，旧重复项转为历史。
- `connectionState`、心跳阈值、数据接入、Kafka/Flink 分析链路与多租户作用域不变。
- 45 号迁移同时挂入 PostgreSQL 空卷初始化和安装器已有卷升级流程。
